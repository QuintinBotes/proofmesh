# Provenance

Project-authored for Proofmesh. Apache-2.0. No third-party code, and `typeorm` is not installed: the rule recognises TypeORM's decorators by the module their import names, so the fixture needs no package.

`expected.json` is hand-written from the fixture code and never generated by Proofmesh. Table names follow TypeORM's default naming strategy, which snake-cases the class name when the decorator names no table (`OrderLine` is `order_line`); those mappings are marked inferred, because a DataSource may install another naming strategy. `@Entity({ schema: 'billing' })` keeps the convention name under the schema it gives.

`OrderSummary` in `src/reports.ts` maps to `orders`, which `src/entities.ts` declared first, through a namespace import (`orm.Entity`). `AuditEntry` uses an aliased import (`Table`) with a name that is not a string literal, so its mapping stays unresolved. `Draft` uses a local decorator that shares TypeORM's name, as a decoy: it maps nothing. `CardPayment` is a `@ChildEntity()` of `Payment` (single-table inheritance), so it shares `payment` through `inherits`.

Static reach (A9). `src/server.ts` is an Express application whose `POST orders` route runs an inline handler that calls `placeOrder`, which constructs an `Order`: the endpoint reaches `orders` at depth 4 (table, entity, `placeOrder`, handler, endpoint). `src/payments.controller.ts` is a NestJS controller whose `POST payments` action calls `chargeCard`, which constructs a `CardPayment`, a child entity of `Payment`: it reaches `payment` at depth 5, one step further through `inherits`. Nothing reaches `sales.clients`. Neither `express` nor `@nestjs/common` is installed either.

`src/data-source.ts` holds a `DataSource` shaped like TypeORM's own, with `initialize`, `destroy` and `isInitialized`. It decorates nothing and maps no table; Observatory's keyboard test opens `DataSource.initialize` from it (#43).
