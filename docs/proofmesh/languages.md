# Languages and what Proofmesh knows about them

This is the capability statement for each ecosystem (FR077). Every file in a snapshot also records its own capabilities, and those are what queries report: a file can fall short of its adapter's statement, for example when a package it imports is not installed.

No adapter runs a project's code, build, or package manager, unless a person grants a repository build evaluation (D14), which only the C# adapter uses.

## Generated and vendored code (FR290 to FR299)

One policy for every language, stated in `workspace_status` as `analysis.generated_policy`:

- Generated files are indexed and flagged. A file is generated by a marker in a comment within its first 5 lines and first 1 KB (Go's `// Code generated ... DO NOT EDIT.`, `@generated`, `<auto-generated`), by the name of a known generator's output (`*.pb.go`, `*_pb2.py`, `*_pb2_grpc.py`, `*.g.cs`, `*.Designer.cs`) or by `linguist-generated` in a `.gitattributes`. Its capabilities say `generated`, every answer row that names it says `generated: true` (a lean row says `generated`), and hubs leave it out unless `include_generated` is true.
- Vendored files are excluded by rule: `vendored:go_vendor` (a `vendor/` directory beside `vendor/modules.txt`), `vendored:third_party`, `vendored:pods`, `vendored:linguist_vendored`. A Go import of a vendored package resolves as an external package of the module `vendor/modules.txt` names, with `detail.vendored`. Calls into a vendored package stay unresolved.
- `linguist-generated` or `linguist-vendored` set to false in a `.gitattributes` overrides every other generated and vendored rule; git ignore stays the stronger exclusion.
- `build/` is output only beside a Gradle manifest (`build_output:gradle`) or when git ignores it; Maven's `target/` only beside `pom.xml` (`build_output:maven`); a directory holding `CMakeCache.txt` is `build_output:cmake`. Any other `build/` directory is source and is indexed.
- The census counts the generated and vendored files of each language.

## TypeScript and JavaScript

The TypeScript compiler's type checker, over every `tsconfig.json` and `jsconfig.json` in the repository, or a default project without one.

- Symbols: functions, classes, methods, interfaces, enums, type aliases, variables and modules, with signatures. Interface members (method signatures, and property signatures holding a function type) and abstract members are `method` symbols named like class members (`<module>:<Interface>.<member>`); an overloaded member is one symbol, which every overload resolves to (FR083).
- Imports: resolved to files in the repository, or to a package; an import of a package that is not installed is unresolved with `dependency_missing`. Each import has a kind: `static`, `type_only` (`import type`, `export type`), `re_export` (`export ... from`) or `dynamic` (`import()` with a literal or no-substitution template specifier); an `import()` with a computed specifier is unresolved with `dynamic_specifier`. A Node.js built-in (`node:fs`, or a bare name such as `path`) is the external module `node:<name>`, with or without `@types/node`, unless a tsconfig `paths` entry maps the name to a repository file, which it then is, as tsc resolves it. An import of a repository file that is not indexed, such as a JSON data file, is unresolved with `not_indexed`; one the snapshot excludes by rule is `import_unresolved`, because the adapter reads only the files the snapshot captures. CommonJS `require()` and `import x = require()` are not recorded as imports.
- Calls: resolved to their declarations, including calls through instances whose type the checker infers. The checker reads installed packages' type declarations from `node_modules`, and each package version is an external input of the snapshot (A2).
- Heritage (FR084, FR085, FR087): a class `implements` each interface its `implements` clause names and `inherits` the class it extends; an interface `inherits` each interface it extends; each is cited at the clause, one row per declaration named. A call through a value typed as an interface or abstract class resolves to that member. A concrete member `implements` or `overrides` each member of its name declared by a class or interface above it, at any distance, so a caller query on it also lists the calls through those members, marked `via`; an abstract member links nothing and is never a dispatch target, and a static member neither links nor is linked, since a call to it names its class. Only declared clauses count: a class that satisfies an interface structurally gets no `implements` and no dispatch rows; a member inherited from a class that does not itself implement the interface is not linked to it; a typed constant's member that names a function instead of defining one (`{ find }`, `{ find: findImpl }`) is not a symbol, so that function is not linked to the interface member; members declared through mapped or intersection types are not symbols, so a call to one stays resolved to the declaration the checker returns, such as the type alias that holds it.
- References (FR086, FR101): a use of a repository class, interface, enum or type alias other than its declaration (type annotations, generics, `implements` and `extends`, `satisfies`, `as`, `typeof`, `new`, and value uses such as an enum member read) is a `references`, one per user and target at its first site, with its uses in `detail.use`. A use of a repository variable (read or assigned), and a function or method used as a value without being called (passed, assigned, a JSX attribute), is a `references` too, with use `value`; a call is a `calls` and a JSX tag a `renders`. Import and export specifiers, re-exports included, are not references. Uses of properties that are not methods are not recorded, so every file reports references as partial.
- React (A20): `renders`, `uses_hook`, `provides_context` and `uses_context`, from JSX, `lazy`, hooks, and `createContext`.
- Prisma Client (A36): the adapter reads the repository's `*.prisma` files as configuration and names each model's table as the Prisma rule does. A model access `client.<model>.<operation>(...)` on a client typed or created as `PrismaClient` from `@prisma/client`, or as a repository class whose extends chain reaches it (NestJS's `PrismaService`), is a `references` (rule `prisma_client`) from the enclosing function to a `table` symbol of that name, declared at the first access. An accessor naming no model is unresolved. Clients through aliases, factories, `$extends` or a transaction's parameter are not recognised, and one model map serves the whole repository.
- HTTP endpoints (A7): Express routes (`app.get('/path', ...)` and the other verbs on an `express()` app or an `express.Router()`, `all` as `ANY`, routers mounted with `use(prefix, router)` composed across modules) and NestJS controller actions (`@Controller('prefix')` with `@Get(':id')` and the other verb decorators) are `endpoint` symbols named `VERB path`, `:param` written `{param}`, each `exposes` its handler (rules `express_route`, `nestjs_route`), as the C# rules shape them. An inline handler becomes a function symbol named after its registration. A path or mount prefix that is not a literal, or a router no application mounts, stays unresolved with the reason. CommonJS `require('express')`, `app.route(...)` chains, receivers held in parameters or properties, routers returned by calls, Express 5 path syntax, and NestJS global prefixes, router modules and versioning are not modelled; Koa is not recognised.
- TypeORM tables (A9): `@Entity()`, `@Entity('name')` and `@Entity({ name, schema })` map their class to a `table` symbol (rule `Entity`); a bare `@Entity()` takes TypeORM's default name, the class name in snake case, marked `inferred`. `@ChildEntity()` `inherits` its parent and shares its table. The decorators are recognised by their import from `typeorm`, so it need not be installed; a decorator re-exported through a local module is not followed.
- Pulumi (A8, A25): each resource a program constructs is a `resource` symbol named by its type and name, as its URN names it. A resource `references` each resource whose outputs its arguments read, and `depends_on` each resource its `dependsOn` option names.

## C#

Roslyn, over the solution's projects, with no restore and no build unless the repository is trusted for build evaluation.

- Symbols, inheritance, interface implementations and overrides; calls resolved to declarations in the repository. A call into a package that would need a restore or generated code is unresolved.
- Framework rules: ASP.NET Core endpoints (`exposes`, `maps_to`), dependency injection (`registered_as`, `injects`), Entity Framework tables, hosted services (`runs`), MediatR (`dispatches_to`, `handles`), Kafka (`publishes`, `consumes`), configuration (`reads_config`), package references (`depends_on_package`), named HTTP clients (`AddHttpClient("name")` gives a `service` symbol and `calls_service`, rule `http_client_name`), and Pulumi resources (`new T("name", ...)` for a type deriving from Pulumi's `CustomResource` or `ComponentResource`, named as the TypeScript rules name them, with `references` and `depends_on`).
- References: a use of a repository declaration other than a call (a type named, a property or field read or written, a constant or enum member used, an object created, an attribute, a method passed as a delegate, a `nameof`) is a `references` relationship, one per user and target at its first site, with its uses in `detail.use`. Enum members are `field` symbols. Names that bind outside the repository, or not at all, are not recorded, so the capability is partial.
- A call that does not bind carries the name it calls (`detail.callee`), its argument count (`detail.arity`) and the compiler's first error inside it (`detail.compiler`); a failure caused only by a name that does not bind is blamed on that name. `nameof(...)` is not a call.
- A repository's conventions file adds jobs, feature flags and code-declared owners (see `conventions.md`).

EF6 entities without an explicit mapping get the pluralised table name by a simple English rule, marked `inferred` in the mapping's detail, unless the context removes the pluralizing convention. A context that names tables through a lightweight convention (`modelBuilder.Types().Configure(c => c.ToTable(...))`) is evaluated when the name is built from constants and `c.ClrType.Name`; a name built from `Helper(c.ClrType).Name` is taken as the entity's own name and marked `inferred`, because the helper may map a type to another, and a schema that is not a compile-time constant is left out and noted. Any other convention leaves `maps_to` unresolved as `outside_capability`; a repository-specific extension installed with `proofmesh extension add` can supply those tables, and `get_table_reach` says so when a snapshot has no table at all. A package reference written with an MSBuild property (`$(Name).Core`) is recorded as an unevaluated input, not a missing one.

## Python

Tree-sitter for declarations and imports, and Pyright's language server for the target of every call. Pyright starts with an empty `PATH`, so no interpreter, and no start-up file of any environment, ever runs.

- Symbols: modules, classes, functions and methods, with their headers as signatures. An empty file, such as a bare `__init__.py`, has no symbol.
- Imports: resolved to files in the repository, for relative and absolute imports, including a package's `__init__.py`. Imports of the standard library and of packages are not reported, so a file that has them reports its imports as partial.
- Overrides (FR226): a method `overrides` the method of its name on each base branch above its class that declares it, found through the bases Pyright resolves to repository classes, so a call through the base is a dispatch caller of the override (a callers query lists it marked `dispatch` with `via` the base method; impact lists it as a `calls` dependent). A static method, a property, a method that overrides nothing and a base outside the repository give no row.
- Calls: resolved across modules, including methods on instances whose type Pyright infers. A call into the standard library or an installed package is `resolved_external`. A call into a package that is not installed is unresolved with `dependency_missing`, and a callee read from a variable or attribute whose value is not known statically is unresolved with `untyped_receiver`. `getattr(...)()` is `dynamic_element_access`.
- Pyright is given 60 s per definition request; a call it does not answer in time is unresolved with `outside_capability` and the file says so in a warning. Pyright is replaced after every 40 files, because a long session answers ever more slowly on untyped code. `PROOFMESH_PYRIGHT_UNANNOTATED=off` makes Pyright skip unannotated function bodies, trading resolution inside them for bounded time.
- Installed packages: read, never run, from the repository's `.venv` or `venv`. Each distribution is an external input. An editable install of the repository's own package resolves to the indexed copy of that package, never to the checkout its `.pth` file names.
- HTTP clients (A7): a call whose name says the verb (`get`, `post`, `_push`, `request`, ...) with a path literal, an f-string or a module constant as its first argument becomes an `endpoint` symbol (`VERB path`, interpolations as `{param}`) and an outbound `dispatches_to`, for the workspace link rules to match. The path starts with `/` or a scheme, or is a route relative to a base URL (`rates/add`); `request("POST", path)` takes its verb from the first argument. A path built any other way is not reported, nor is a decorated route (`@router.get("/x")`) or a route registration, which declare what the service exposes.
- Inheritance: a class `inherits` each repository class Pyright resolves a base to.
- Entry points (A7, A9): FastAPI routes on `FastAPI()` apps and `APIRouter(prefix=...)` routers composed by `include_router` (rule `fastapi_route`), Flask routes on apps and blueprints with their registered prefixes (`flask_route`), and Django URLconfs from `ROOT_URLCONF` through `include()` (`django_path`) are `endpoint` symbols named `VERB path` that `expose` their handlers; a Django function view is `ANY path`, and a class-based view exposes each of its own verb methods. Celery `@shared_task` and `@app.task` functions are `job` symbols that `run` them. Path converters take the ASP.NET form (`<int:id>` as `{id:int}`, a path converter as a catch-all). A router or blueprint nothing mounts is placed at the root, marked `inferred`. A route, method list, prefix or URLconf the rules cannot read stays unresolved on its handler, and `re_path` is skipped with the reason. Routes added by call (`add_api_route`, `add_url_rule`), `app.mount`, Django REST framework and included lists are not read.
- Tables (A9): SQLAlchemy `__tablename__` (rule `tablename`), a module-level `Table("name", ...)` (rule `table`, its variable the entity) and `__table__` (rule `table_attribute`); Django models in an app's `models.py` or `models/` package, by `Meta.db_table` (rule `db_table`) or else `<app_label>_<model>` (rule `django_convention`, marked `inferred` unless `Meta.app_label` names the label). Each table is one `table` symbol declared at its first mapping, and `maps_to` runs from each entity to it. Single-table subclasses and Django proxy models map nothing and reach their parent's table through `inherits`; abstract models map nothing. Django and SQLAlchemy need not be installed: their classes are recognised by import. Schemas, `@declared_attr` names, mixins, Flask-SQLAlchemy's automatic names and imperative mappings are not read.
- Pulumi (A8, A25): resources constructed from a `pulumi_*` provider package, named through the imports, or from a repository class deriving from a Pulumi resource, named as the TypeScript rules name them; `references` from an argument that reads another resource's output, and `depends_on` from `ResourceOptions(depends_on=[...])`. An `opts` held in a variable is not followed, and resources of the core `pulumi` package such as `StackReference` are not recognised.
- A repository's conventions file adds jobs, feature flags and code-declared owners (see `conventions.md`).
- Incremental indexing (A16): an edit reanalyses the edited file and every file that imports it, directly or not. Adding or removing a module reanalyses every Python file.

## Terraform

Static HCL through Tree-sitter. Proofmesh never runs `terraform init`, so remote modules are not fetched.

- Symbols, named by their Terraform address within their module directory: resources and data sources (`resource`), variables and locals (`variable`), outputs (`output`), module calls (`module_call`), and each file (`module`).
- References: from a block to each variable, local, resource, data source and module output it reads; an undeclared name is unresolved with `unknown_name`.
- `depends_on`: from each `depends_on` entry, and from a module call to the files of a local child module. A remote module call is unresolved with `dependency_missing`.
- The link from cloud resources to the services that run on them waits for M6 (A26).

## The syntax tier

Tree-sitter grammars on WebAssembly (A6, A23) for Java, Go, Rust, Ruby, PHP, C, C++, Bash, Scala, Kotlin, Swift and SQL, and for Prisma schemas. The TypeScript, TSX (which also reads JavaScript and JSX) and C# grammars are the floor under their precise adapters, below.

- Symbols: the declarations each grammar's tags query finds.
- Calls: every call site, with the callee's name as detail, unresolved with `outside_capability` unless constrained name matching binds it (below). The syntax tier never claims a call target as `resolved`. A Java `new T()` is a call of `T`. In Go and Java the detail also holds `qualifier` (the identifiers written before the name), `receiver` `expression` (when the operand is not a plain name), `shadowed` `local` (when a variable, parameter or field of that name is in scope) and `form` `new`. A Rust call through a path (`ffi::f()`, `Foo::new()`, `crate::util::f()`, `<T as Tr>::f()`) is a call of its last name, with the path before the last `::` as written in `qualifier` (FR500, FR501).
- Imports (FR115): one `imports` row per import statement, from the file, with the module as written in `detail.module` (a Java wildcard ends in `.*`, a Go alias is `detail.alias`). Each is unresolved with `outside_capability` (FR117) unless constrained name matching binds it (below), so a file in Go or Java reports its imports as partial, with or without an import statement, and nothing reports them complete. A Java static import carries `detail.static` `true`, and a Go dot or blank import has `detail.alias` `.` or `_`.
- Heritage (FR116): a Java class `inherits` the class it extends and `implements` each interface it names, as do a Java enum and record; a Go struct `inherits` each type it embeds, with `detail.relation` `embedding`. Each row runs from the declaring type, at the supertype's name, with that name in `detail.name`, and is unresolved with `outside_capability` (FR117) unless constrained name matching binds it (below). A Java interface's `extends` and a Go interface's embedded interfaces are not recorded yet.
- Kotlin, Rust, PHP and Ruby (FR221, FR222): an import is one `imports` row per statement. A Kotlin import keeps a wildcard (`com.a.*`) and an `as` alias; Kotlin allows no import inside a function. A Rust `use` is one row, also inside a function body, at its own line: a grouped `use crate::geo::{Point, Line};` has the path as `detail.module` and the text between the braces as `detail.names` (`Point, Line`, nested groups as written), `use a::b as c` has `detail.alias`, and `mod geo;` is module `geo` (an inline `mod x { }` is none). A PHP `use` is one row per clause, with `detail.alias`, and a group `use A\{B, C}` has the prefix as module and the clauses as names; `use function` and `use const` are not told apart. A Ruby `require` or `require_relative` with a string is a row (the string's content, however it is delimited, `"x"` and `%q(x)` alike); one with any other argument is not, and each is still a call. Heritage: a Kotlin class, interface or object `inherits` each supertype in its list, with `detail.relation` `supertype`, except the one a constructor call names, which is a plain `inherits`, because the tier cannot tell a class from an interface otherwise; type arguments are dropped from the name, and a named companion object is a class symbol that owns its supertypes, and an unnamed companion object or object expression names nothing. A Rust `impl Trait for Type` is an `implements` row from `Type` when this file declares it, and otherwise from the file's module with the type in `detail.for`; a written path (`impl Shape for b::Thing`) must match the module the type is declared in (`crate`, `self` and `super` are read), and an ambiguous owner is not guessed; a trait's bounds (`trait Named: Shape`, also `for<'a> Bound<'a>`) are `inherits` rows from the trait. A PHP class `inherits` what it extends and `implements` each interface, and an interface `inherits` each it extends; an enum's `implements` and a class's `use Trait;` are not recorded. A Ruby class `inherits` its superclass, and `include` inside a class or module is `inherits` with `detail.relation` `include`, and `detail.conditional` `true` when an `if` or `unless` (modifier or block) wraps it (`extend` and `prepend` are not recorded). A file the grammar parses in part keeps the facts of the parsed part, with syntax partial.
- Swift, Scala, C, C++ and Bash (FR231 to FR233): an import is one `imports` row per statement. A Swift `import` keeps its module (`import struct Foo.Bar` is `Foo.Bar`, and an attribute such as `@testable` is dropped). A Scala `import` is one row whatever it names: the path as written is `detail.module`, a wildcard ends it (`a.b._`, `a.b.*`), `import a.b.C as D` is module `a.b.C` with `detail.alias` `D`, and braces give the path as module and the text between them as `detail.names` (`C => D, E`), but a statement of several clauses (`import a._, b.C`) is one row with its module as written; an import inside a function body is a row at its own line, and `import a.B, c.D` is one row with the module as written. A C or C++ `#include` of `<x.h>` or `"x.h"` is module `x.h` with `detail.system` `true` or `false`, and `detail.conditional` `true` when an `#if`, `#ifdef`, `#elif` or `#else` wraps it, except a real include guard (`#ifndef X` then `#define X`, wrapping the whole file); an include of a macro is none. A Bash `source` or `.` of a word, a quoted string without an expansion or a single-quoted string is a row, the first argument only; a path with an expansion (`"$DIR/x.sh"`) or an unquoted glob (`*.sh`) names no module and is not a row, and each is still a call. Heritage: a Swift class, struct, enum, actor or protocol `inherits` each type in its list with `detail.relation` `supertype`, because the tier cannot tell a class from a protocol, with generic arguments dropped; an extension's list is not recorded. A Scala class, trait, object or enum `inherits` the type after `extends` and `implements` each after `with` or a comma, with type arguments dropped and a qualified name as written. A package object's `extends` is not recorded, because the tier has no symbol for it. A C++ class or struct `inherits` each base, with the access and `virtual` dropped, a qualified base as written (`ns::D`) and template arguments dropped; C has no heritage. Calls (FR233): a C or C++ call of a name is a call row from the function or method whose body holds it, the callee being its last identifier (`ns::f()` and `f<T>()` call `f`, `p->f()` and `o.f()` call `f`, as do `p.template f<T>()` and `T::template f<U>()`), and a method defined outside its template class, `A<T>::f`, is named `A.f` so the calls in its body run from it; a macro call such as `MAX(a, b)` is a call like any other, a call through a pointer or an expression with no name, `(*fp)(x)`, is none, and a C++ `new T()` is none. A file the grammar parses in part keeps the facts of the parsed part, with syntax partial.

- Names (FR146): every symbol's qualified name is the one the SCIP importer also gives it. Java, Kotlin, Scala and PHP start from the declared package or namespace (Scala's nested and chained packages and PHP's several namespaces are each declaration's own); every other language starts from the file path. A Go method is named under its receiver type, a Rust method under its `impl` type and, in a trait impl, the trait (`X.<Display>.fmt`), and a C++ member defined outside its class under that class. Overloads of one name in a file take their parameter types, as written. Limitation: a C or C++ prototype is merged into its definition only inside one file, so a prototype in a header and its definition in a `.c` file stay two symbols, one per file.

What the tier records per language (FR118):

| Language | Imports | Heritage | Calls |

| Rust | `use` and `mod x;`, with module, alias and grouped names | `impl Trait for`, trait bounds | yes |
| PHP | `use`, with module, alias and grouped names | `extends`, `implements` | yes |

- Grammars: each is pinned by its package version and the hash of its WebAssembly, which join the adapter's identity. Swift, SQL and Prisma ship no WebAssembly, so `adapters/syntax/grammars/rebuild.mjs` builds them from their packages' source with the Tree-sitter CLI 0.27.2; the build is reproducible, and the syntax adapter's build refuses a grammar whose hash or version differs from `grammars/built.json`, or whose license `policy/licenses.json` does not allow. Each grammar's license text ships beside it, and `THIRD_PARTY_NOTICES.md` lists every grammar.
- Swift: classes and actors, structs, enums, protocols, functions, methods and properties; members of an `extension X` are named `X.member`. Imports are unresolved import statements. Initializers, subscripts, enum cases and top-level `let` and `var` are not symbols.
- SQL: `CREATE TABLE`, `VIEW` and `MATERIALIZED VIEW` are `table` symbols named by their schema-qualified name, and functions and procedures are functions. A table named in FROM, JOIN, UPDATE, INSERT INTO, DELETE FROM or a `REFERENCES` clause is a `references` candidate when the same file declares it, and unresolved otherwise. T-SQL bracket identifiers do not parse, so such names are skipped and the file reports partial.
- Prisma (A9): each model and view is a class that `maps_to` a `table` symbol: the name `@@map` gives (rule `prisma_map`) or else the model's own (rule `prisma_convention`, marked `inferred`), qualified by `@@schema`. A field whose type is a model in the same file is a resolved `references`; a relation to a model another file declares is unresolved. Prisma Client calls in TypeScript reach these tables (see the TypeScript section).

## The syntax tier as the floor under TypeScript, JavaScript and C#

The TypeScript, TSX and C# grammars are shipped too (FR310), but the tier reads these languages only when their precise adapter cannot (FR311, FR313, FR314); a file the adapter analyses never reaches it (FR318).

- A file goes to the syntax tier when its adapter is unavailable (no .NET SDK, the adapter missing), answers `failed` for it, dies, runs out of restarts or cannot start. The rest of the repository keeps its precise facts, and the snapshot publishes. A file the adapter had already analysed before it died keeps its facts.
- Each such file records tier `syntax` and why in its disposition detail: `adapter_unavailable:<adapter>`, or `adapter_failed:<adapter>` with the adapter's own detail after it. The census row names the same reason with its remedy (FR312); the finished job's result, a line of `proofmesh index` and the snapshot's meta `fallbacks` give the adapter, the number of files and the stored failure, never the adapter's stderr (FR314). For an adapter that is not built, the result and the line add what is missing and where it was looked for: `adapter_unavailable:csharp (not built: looked in <paths>)`; the file rows, census and meta keep the bare reason (FR385).
- Facts: declarations, call sites without targets, imports (`import` and `export ... from`, `require`, C# `using`), and TypeScript `extends` and `implements`. Framework rules (routes, dependency injection, EF) and resolved calls are `unsupported` on these files (FR319). C# heritage needs the precise tier, because a base list does not say which base is an interface.
- Keys are the precise tier's: TypeScript names are `<module>:<Class>.<member>`; C# names are in namespace form, read from the source (block and file-scoped namespaces, nested types, a generic type with its parameters, an overload not told apart by parameter types), so every declaration the syntax tier finds has the key Roslyn gives it (FR316). Roslyn adds the projects and generated members. When the adapter comes back the files move to the precise tier with their keys unchanged, a note on them reads `tier_changed`, and the index equals a clean one (FR315).
- A snapshot degraded by a crash is never the answer to a later index: the next index asks the adapter again under a new `retry` number, and an adapter that is merely unavailable is part of identity as before. An adapter that cannot answer workspace gives all its files to the syntax tier.

## The syntax tier: constrained name matching in Go and Java

The syntax tier never knows a call's target, so for Go and Java a pass over the whole workspace binds a name only where the language's own rules allow it (FR171 to FR180). It reads facts the other adapters recorded, the build graph (which module holds each file, which modules each declares a dependency on), each file's package and imports, and the modifier on each declaration, and it runs on every index, so an incremental index equals a clean one. A name match is never `resolved`: one reachable target is a `candidate`, several are `ambiguous`, and every such row names its rule in `detail.rule` and is `inferred` in the `basis` every answer gives (see Relationship basis in `mcp.md`), so no edge is made of it and a reader can tell it from a compiler's answer. A row no rule can judge keeps the row the tier wrote.

- Modules (FR172): no row binds to a module the source's module has no `depends_on` to. A name only such a module holds is `unresolved` with `dependency_missing` and `detail.undeclared` naming the project. Files that no build manifest contains see each other.
- Cap (FR176): a site lists at most five candidates, ranked by rule (same file, import, same package, wildcard), then path and position; with more it is `ambiguous`, lists the first five and gives the rest as `detail.more`.
- Kinds (FR175): `new T()` binds only types and a method call only methods.

| rule | what it binds |
|---|---|
| `go_package_member` | `pkg.Name(...)` to the exported function `Name` of the package the import names; an embedded `pkg.T` to its exported type. An unexported or missing name is `unresolved` `unknown_name` with `detail.visibility` |
| `go_same_package` | a bare call to a function of the same package (the same directory and package clause; a test file's own declarations stay in test files), an embedded `T` to a type of it |
| `go_dot_import` | a bare call to an exported function of a dot-imported package; a blank import binds nothing |
| `go_import_path` | an import whose path lies in a module of the repository the importer declares a dependency on. An import links files and a Go package is a directory, so the row is a candidate (ambiguous when the package has several files) listing the module symbols of the package's non-test files, with `detail.package` the directory and `detail.files` the count; a file a `//go:build ignore` constraint keeps out of every build is no part of it. An `internal` package imported from outside the parent of `internal` is `import_unresolved` with `detail.visibility` `internal`, and calls through it are `unknown_name` with the same |
| `java_same_file`, `java_import`, `java_same_package`, `java_wildcard_import` | a simple type name, in that order; a single-type import hides a same-package type of the name, also when the repository does not declare the imported type (`java.util.List`). They bind `extends` (a class), `implements` (an interface), `new T()` and the type of `T.m()`; a Java import by name is a `candidate` with `java_import` |
| `java_same_class` | `m()` and `this.m()` to the innermost enclosing type that has the method, its own and inherited ones together (overloads), else `java_static_import`. When a supertype is not in the repository the search cannot be complete: what it finds is `ambiguous` even with one candidate, and it never falls through to a static import, which an inherited method would hide |
| `java_inherited` | `super.m()`, and `T.m()` where `T` only inherits the method |
| `java_static_import` | a bare `m()` or an `import static` to a static method of the imported type |
| `java_qualified_name` | a fully qualified type name |

A call whose receiver is a variable, a field, a call result or any other expression has a type the tier does not know, and binds to nothing whatever types of the repository have a method of that name (`buf.Write()`, `err.Error()`, `list.add()` keep `outside_capability`). A variable that hides a package or a type is `detail.shadowed` `local`.

Go builds no package from a `vendor` or `testdata` directory, or one starting with `.` or `_`; none is matched, and an import of one keeps its row.

Dependencies (FR172): a module sees the modules the build graph records a direct, resolved `depends_on` to, and no others. A dependency of the test scope (Maven `<scope>test</scope>`, a Gradle `test...` configuration) is seen by test sources only (`src/test` and the like), and one of the runtime scope by none, so a name only such a module holds is `dependency_missing` for a main source. A transitive dependency is not seen: a module that uses a type of a module it reaches only through another gets `dependency_missing` until it declares the dependency, as a Go module must list what it imports.

Java visibility: `private` within the top-level class, package-private within the package, `protected` in the package or by inheritance, `public` always, and an interface member without `private` is public. A type is reachable when it and every type around it is public or in the file's package. A name the repository does not declare (the JDK's, a library's, a package outside it) keeps `outside_capability`. Kotlin, Rust, PHP, Ruby, C and C++ are not covered yet; their rows stay as the tier wrote them.

`workspace_status` gives `module_cycles` (FR178): each cycle among the build modules of an ecosystem whose builds forbid one (Maven, Gradle, Go modules, Cargo, .NET) that these rows form, with the edges that form it, and a warning in `limitations`. It is empty on a repository whose declared dependencies do not loop.

## The build graph: JavaScript and Go modules

The build adapter (FR124 to FR129) reads manifests as captured text and never runs a build tool, package manager or script, so a `preinstall` script in a `package.json` is data (FR079).

- Projects: a `package.json` that names a package and a `go.mod` are `project` symbols, named by the npm name or the Go module path and declared at the line of that name. A `package.json` with no name (a workspace root, or a `{"type": "module"}` marker) declares none and does not hide the project above it. Manifests under `testdata` and `vendor` directories declare none.
- Containment: each source file is contained by the project of its nearest enclosing manifest that declares one, so `analyze_impact` groups dependents by project. A file under none is contained by none. A directory with both a `go.mod` and a `package.json` gives its files to the Go project.
- Dependencies inside the repository (`depends_on`, resolved, at the declaring line): a `package.json` dependency on a workspace member (the root's `workspaces`, as an array or `{"packages": [...]}`, or a `pnpm-workspace.yaml` `packages` list read line by line; `**` matches zero or more directories, `{a,b}` either, `!` excludes), a `workspace:` dependency when the repository lists no workspaces at all (any named package), or a `file:` or `link:` to a project directory; a `tsconfig.json` `references` entry, to the referenced directory's own project only (its `extends` is not read); a `go.mod` `require` that a local `replace` (in the `go.mod` or a `go.work` that uses the module) or a module the same `go.work` uses satisfies. A path outside the repository, or into a directory with no manifest, is unresolved with `dependency_missing` and the path as written; two projects of one name make a dependency on it ambiguous.
- Packages outside it (`depends_on_package`, `resolved_external`): `npm:<name>` and `go:<module>` with the declared version in `detail.version`; a `file:` or `link:` to a tarball or to a directory that is no project is a package, with the spec as its version. A Go `require` that no `go.work` or local `replace` satisfies is a package even when a repository module has that path, because Go would fetch it.
- A manifest that does not parse fails that file with the line in its disposition detail; every other manifest is still read.
- Not read yet: a dependency list a script edits. Rust, Python, PHP and Ruby manifests, then Maven, Gradle, Bazel and Buck, are read below.

## The build graph: Rust, Python, PHP and Ruby manifests

The same adapter reads `Cargo.toml`, `pyproject.toml`, `composer.json` and `*.gemspec` as captured text (FR240 to FR245, FR249). It runs no Cargo, `build.rs`, `setup.py`, pip, Composer or Bundler and makes no network request, so a `build.rs` or `setup.py` that would write a marker if run leaves none (FR079). TOML is read by a purpose-built reader in the adapter (comments, quoted and dotted keys, literal and multi-line strings, inline and nested arrays, arrays of tables), not by a Tree-sitter grammar, so the adapter adds no grammar or dependency.

- Projects, each at the line of its name: a `Cargo.toml` with `[package] name`; a `pyproject.toml` with `[project] name` or `[tool.poetry] name`; a `composer.json` with `name`; a `*.gemspec` with a literal `name =`. A virtual Cargo workspace root, a `pyproject.toml` that only configures a workspace or tools, and a manifest under `testdata` or `vendor` declare none. Containment is as for JavaScript and Go: the nearest enclosing manifest that declares a project.
- Cargo: `dependencies`, `dev-dependencies` and `build-dependencies`, also under `target.*`. A `path` dependency is a `depends_on` to the crate in that directory (`dependency_missing` when it is outside the repository or holds no crate); any other is `cargo:<name>` (`package` renames) with its version, and dev and build dependencies carry `detail.scope`. `workspace = true` takes its spec from the `[workspace.dependencies]` of the nearest workspace root that lists the crate in `members` and not `exclude`. Not read: members a path dependency adds implicitly, `[patch]`, `[replace]`, and `Cargo.lock`.
- Python: PEP 621 `dependencies`, `optional-dependencies`, `[dependency-groups]`, uv `dev-dependencies` and Poetry's dependency tables become `pypi:<name>` with the version specifier (extras and markers cut). A uv `[tool.uv.sources]` entry of the manifest or its workspace root turns a requirement into a `depends_on`: `workspace = true` to the member of that name (`members` minus `exclude`), `path` to the project in that directory. A `dynamic` list that names `dependencies` or `optional-dependencies` is an unresolved `dynamic_specifier` row at its line and the file reports `partial`. `setup.py` and `setup.cfg` are not read for dependencies; `setup.py` stays Python source.
- PHP: `require` and `require-dev` become `composer:<name>` with the constraint, except platform requirements (`php`, `ext-*`, `lib-*`) and a package a `path` repository of the manifest brings from a project of the repository, which is a `depends_on`. `autoload` and `autoload-dev` `psr-4` and `psr-0` entries are `reads_config` rows from the project whose `detail` has `autoload`, `prefix` (as written) and `path` (from the repository root, with a trailing `/`), for later name resolution. `classmap` and `files` are not recorded.
- Ruby: a gemspec is code, so only `name =` and `add_dependency`, `add_runtime_dependency` and `add_development_dependency` lines are read, as patterns, and every fact has `detail.inferred` of `gemspec_pattern`. A dependency on a gem another gemspec of the repository names is a `depends_on`, any other `gem:<name>` with its literal requirements; a requirement that is not a literal is `detail.version_expression`, and a call whose gem name is not a literal (a loop, a variable) is an unresolved `dynamic_specifier` row and the file reports `partial`. A `Gemfile` is not read.
- A `Cargo.toml` or `pyproject.toml` that is not valid TOML fails with `invalid_toml:line N`, and a `composer.json` that is not valid JSON with `invalid_json:line N`; every other manifest is still read.

## The build graph: Maven and Gradle modules

The build adapter reads `pom.xml`, `settings.gradle(.kts)`, `build.gradle(.kts)` and `gradle/libs.versions.toml` as captured text (FR151 to FR160). It starts no Maven, Gradle or JVM and evaluates no build file, so a plugin, task or top-level statement that would write a marker if run leaves none (FR079). A Gradle script in Kotlin goes to the adapter as a manifest, not to the syntax tier as Kotlin source.

- Maven projects: a `pom.xml` is a `project` named `groupId:artifactId`, the group inherited from its parent, declared at the line of its `artifactId`. The pom is read by a bounded XML reader: a DOCTYPE is skipped and never expanded, and nesting is capped. A `<module>` with no pom on disk is an unresolved `depends_on` with `dependency_missing`. A `dependency` is a `depends_on` to the repository's project of that name (`ambiguous` for two), else a `depends_on_package` `maven:<group>:<artifact>` with its version. `${...}` is resolved from `project.*` and the literal properties of the pom and its parents, and a version with none takes the `dependencyManagement` version; one left as `${...}` is `detail.version_expression`.
- Gradle projects: each `include` path of a settings script is a `project` named by it (`:app`, `:a:b`) at the include's line; the root project is not declared. A project's directory is its path under the settings file's directory.
- Gradle dependencies: inside `dependencies { }`, the configurations `implementation`, `api`, `compileOnly`, `runtimeOnly`, their test and processor variants, with a string coordinate (or the Groovy map form, or `platform(...)`), `project(":x")`, or a catalog alias `libs.x` and `libs.bundles.x` from `gradle/libs.versions.toml` (one entry per line). Every Gradle fact has `detail.inferred` of `gradle_script_pattern`, since a script is code.
- Not read, and said so: a statement the patterns cannot read (a variable, an interpolated coordinate, a call, an alias the catalog lacks) is an unresolved `depends_on_package` with reason `dynamic_specifier`, `detail.configuration` and `detail.source`, at its line, and its file reports `partial` symbols, which the language census shows. The same holds for an `include` in a block, closure or after a condition (it declares nothing), a build script no settings include owns, an expression `${...}` that cycles or expands past 4 KiB, and for `includeBuild`, `includeFlat`, a computed `include`, `projectDir` and `apply from` in settings, and for `allprojects`, `subprojects` and `apply from` in a build script. Maven profiles and `dependencyManagement` imports (`scope` `import`) are not read.
- Containment: each source file is contained by the nearest Maven module or Gradle project directory above it.
- A `pom.xml` that is not well-formed fails with `invalid_xml:line N`, and a Gradle script with a comment that is never closed with `invalid_gradle:line N`; every other build file is still read.

## The build graph: Bazel and Buck targets

The same adapter reads `BUILD`, `BUILD.bazel` and `BUCK` files as captured text (FR246 to FR249). A build file is code, so it is parsed as Starlark by a small reader that takes only what a literal gives: nothing is evaluated, no `bazel`, `buck` or JVM process starts, and a `genrule` that would write a marker if run leaves none (FR079). The grammar of Python is not used.

- Targets: each top-level rule call with a literal `name` is a `project` labelled `//<package>:<name>` (the package is the directory of the build file; `//:name` at the root), at the line of its name. A `genrule` (or any rule named `*genrule`), `filegroup`, `alias`, `config_setting`, `test_suite` and the like are no build unit and declare none, and a dependency on one is not recorded.
- Files: a target contains the captured files its `srcs`, `hdrs` and `exported_headers` name (a plain path, `:file` or `//pkg:file`) and those a `glob` in them matches (`**`, `*`, `?`, `{a,b}`, `exclude`); a glob does not enter a directory that has its own build file. A file outside every target is contained by none of them, and a target's files are not the whole directory. A name that is no captured file is ignored.
- Dependencies: each literal `deps` and, for Buck, `exported_deps` entry is a `depends_on` to the labelled target (`:x`, `//pkg:x`, `//pkg`, `@//pkg:x`, `root//pkg:x`), `ambiguous` for two of one name and `dependency_missing` for none. A label of another repository (`@maven//:guava`, another Buck cell) is a `depends_on_package` `bazel:<label>` or `buck:<label>` as written. Every `select()` branch is recorded with `detail.condition`.
- Not read, and said so: a call to a macro loaded from a `.bzl` file of the repository, a rule inside a `for`, `if` or `def`, a `name` that is not a literal, a `deps` entry that is not a string (a variable, a comprehension), and a `srcs`, `hdrs` or `glob` that is not a literal each leave the target undeclared or unread and make the file report `partial` symbols with a diagnostic; the language census shows it. A name loaded from another repository (`@rules_java//...`) is taken for the rule it names. `MODULE.bazel`, `WORKSPACE`, `.bzl` files, `runtime_deps` and `data` are not read.
- A build file whose brackets or strings do not balance fails with `invalid_starlark:line N`; every other build file is still read.

## HTTP seams in one repository (FR250 to FR259)

A client and the handler it calls meet inside one repository by the rules the workspace links use across repositories, whatever language each is in.

- Clients: a TypeScript `fetch(...)` or `axios` call (`axios.get(...)` and the other verbs, `axios(...)`, `axios.request(...)`, a client from `axios.create`) whose path is a string, a template, a concatenation or a module constant is an outbound `dispatches_to` of `VERB path` (rules `fetch_client`, `axios_client`; Python's is `http_client`). Scheme, host, query and fragment are dropped, each interpolation is a `{param}`, and the verb is the `method` option's literal, else `GET`. A path on a base held in a variable keeps its suffix with `detail.prefix_unknown`.
- Declarations: an OpenAPI 3.x or Swagger 2.0 document named `openapi`, `swagger`, `*.openapi` or `*.swagger`, as YAML or JSON, declares an `endpoint` per path and verb at the verb's line, the `operationId` in its signature, the base path joined (one endpoint per distinct server path). A `$ref` path item is not followed and makes the file partial; a document that does not parse is `failed` with `invalid_openapi:line N: ...`.
- Links: each client's function is linked by `dispatches_to`, origin `contract_match`, to the handler of the endpoint it names, with `detail.rule` `http_route`, `detail.endpoint` and `detail.confidence`: 1 exact, 0.9 a literal where the server has a parameter or the parameter has another name (they are matched by position), 0.8 another verb, 0.6 a suffix, 0.5 a suffix whose base is unknown and only one endpoint ends so. The same `VERB path` in code and in a document is one endpoint. Several equally good handlers make the row `ambiguous`.
- Boundaries, never guesses: a declared endpoint no code serves is an unresolved `exposes` from the declaration (`declared_without_handler`); a client that matches nothing is an unresolved `dispatches_to` with `unknown_name` and its path, or `not_indexed` when only a declaration with no handler matches. The one exception to code routes is a function named exactly once by the declaration's `operationId`, taken as the handler at 0.7, which is how a Go handler is found until Go has route rules.
- Every row reads as inferred (`basis`), and `analyze_impact`, `find_tests` and `trace_paths` follow it. The fixture is `fixtures/seams-http`.

## Schema-first contracts: protobuf, gRPC and GraphQL (FR400 to FR405)

A protobuf RPC or a GraphQL root field is where services in different languages meet. The contract is read as symbols, and the code that implements it and the code that calls it are linked to it, labelled inferred.

- Contracts: the build adapter reads `.proto` files (package, services, RPCs, messages) and GraphQL SDL in `.graphql` and `.gql` files with a small reader of their text; nothing is compiled, fetched or run. Each RPC is an `endpoint` `grpc <package>.<Service>/<Method>` at the rpc statement (options such as `go_package` never change the name), each message a `message` `<package>.<Message>`, each GraphQL type a symbol named `<module>:<Type>` (`schema:Order`), and each root field (`Query`, `Mutation`, `Subscription`, or the types a `schema` block names) an `endpoint` `graphql <Root>.<field>`. SDL in a TypeScript `gql` template is read the same way. A file that does not parse is `failed` with `invalid_proto:line N` or `invalid_graphql:line N`.
- gRPC servers: a method named like the RPC (in any case) of a type whose supertype is the service's generated base: `UnimplementedSServer` (Go, embedded), `SServicer` (Python), `SImplBase` (Java), `SBase` (C#), `ISServer` or `SServer` (TypeScript). The declared endpoint `exposes` it, rule `grpc_server`, `detail.base` the supertype as written.
- gRPC clients: in a file that constructs the service's stub, `SStub` (Python), `NewSClient` (Go), `SGrpc.newBlockingStub` and the other `new*Stub` (Java), `SClient` (C#, TypeScript), each call named like an RPC of the service (in any case, or with C#'s `Async`) `dispatches_to` the declared endpoint from the calling function, rule `grpc_client`, `detail.stub`.
- GraphQL: the TypeScript adapter reads resolver maps, each function of a `Query`, `Mutation` or `Subscription` object in an object literal, as the resolver of that field (rule `graphql_resolver_map`; an inline resolver becomes a function symbol such as `resolvers.Query.order`), and `gql` operations, each root field they select by name (not alias), through inline and named fragments (rule `graphql_operation`). The declared field `exposes` its resolvers and its operations `dispatch_to` it.
- Every link is a `contract_match` row, read as inferred, and `analyze_impact`, `find_tests` and `trace_paths` follow it: impact on a server method reaches its callers through the endpoint.
- Boundaries, never guesses: a declared RPC or field nothing implements is an unresolved `exposes` (`declared_without_handler`); an operation of a field no contract declares is an unresolved `dispatches_to` with `detail.field`; a field several contracts declare makes its callers `ambiguous`. Generated stubs (`*.pb.go`, `*_pb2_grpc.py`) stay flagged generated and are never taken for implementations.
- Limitations: code-first GraphQL schemas (decorators, builder APIs such as TypeGraphQL, Nexus or graphene) are not read, so their fields are neither declared nor linked; a resolver given as a shorthand property or a `{ resolve }` object is not read; a gRPC stub of a service the repository does not declare is not recognised, so its calls are neither linked nor listed; proto2 groups are not read. The fixture is `fixtures/seams-schema`.

## FFI seams between languages (FR460 to FR467)

A call across a foreign-function interface is linked to the function on the other side by that mechanism's naming rule. The rule is a convention, so every link is a `candidate` (one target) or `ambiguous` (several) `calls` row, origin `contract_match`, never `resolved`, and reads as inferred; `analyze_impact` with `include_inferred` follows it.

The rules, each from the calling side to the called one:

- `jni`: a Java `native` or Kotlin `external` method, at its declaration, to the C function `Java_<class>_<method>` (a `__<signature>` suffix and the `_1`, `_2`, `_3`, `_0xxxx` escapes are decoded).
- `pinvoke`: a C# method `[DllImport]` or `[LibraryImport]` marks, at its declaration, to the C functions of its `EntryPoint`, else of its own name, anywhere in the repository.
- `cgo`: `C.f(...)` in a Go file that imports `"C"`, to the C function `f`.
- `cgo_export`: a C call of `f`, to the Go function a `//export f` comment marks.
- `rust_extern_c`: a Rust call of a function an `extern "C"` block of the same file declares, to the C function of its `link_name`, else its name.
- `rust_no_mangle`: a C call of `f`, to the Rust function `#[no_mangle]` marks.
- `python_c_extension`: `m.f(...)` with `m` imported, or `f(...)` imported from `m`, to the C function a `PyMethodDef` entry `{"f", fn, ...}` of extension module `m` (`PyInit_m`) registers.

- A C target is a definition where the repository has one, else the prototypes that declare it, so a header and its source file do not make a call ambiguous. A call row the rule binds replaces the unresolved row the adapter wrote at that site.
- A declaration or call whose other side is not in the repository (a system library) is `resolved_external`, named by the C function and by the library where the code writes it (the `DllImport` argument, `System.loadLibrary`, `#cgo LDFLAGS: -l`, `#[link(name)]`) in `detail.library`. Where the code names no library, the external's module is empty: the library is never guessed.
- `workspace_status` `data.ffi_seams` counts the rows by rule, linked or external.
- Not done: a P/Invoke library is not matched to a build target; JNI overloads are not told apart by their signature (two overloads of one method are each ambiguous between both C functions); a Rust call through a path (`ffi::f()`) is not linked, because the syntax tier records no row for it (#116); a C function defined in a cgo preamble is taken for an external one; `RegisterNatives` and `ctypes`/`cffi` are not read. The fixture is `fixtures/seams-ffi`.

## SCIP indexes a person produces

A person who runs a SCIP indexer can name its output: `proofmesh scip add <repository> <index.scip>`. Proofmesh reads the file and, for a repository that is not trusted for build evaluation, never runs an indexer (A24).

- An index covers only files no semantic adapter analyses, so it upgrades the syntax tier and languages with no adapter (A27).
- Symbols: each definition, with its kind and signature as the indexer recorded them, named as the syntax tier names the same declaration, so naming an index changes no key (FR148); the index's own symbol stays in `detail.scip`, which `get_symbol` returns (FR441). A definition's span is the indexer's enclosing range; when the index records none, it is the syntax tier's span of the declaration that holds the name, so a line inside the body has an enclosing symbol (FR121).
- References: from the innermost definition that encloses each occurrence, resolved to a definition the index serves, or to an external symbol named by its package. A symbol the index defines in a file whose facts come from another adapter is unresolved with `outside_capability`.
- Calls (FR161): SCIP does not mark an occurrence as a call, so the importer joins the syntax tier's call sites with the index. A call site whose callee name holds a reference occurrence of a function, method or constructor symbol is a `calls`, `resolved` (or `resolved_external` with the package from the symbol), with evidence at the callee name; every other reference stays a `references` row, so a function passed as a value, and a field or variable that holds one, are references, and a local variable is neither. A call to a type is a call to its constructor symbol where the index has one, else to the type (FR168). A call site with no occurrence at its callee name (a stale index, another position encoding) gives no call, and the file's `resolved_calls` is `partial`, with the count in the adapter's warning for the file (FR166). A Java `new T()` and a Go `T{}` literal are such calls: to `T`'s constructor symbol where the index has one, else to the type `T` (FR530).
- Inheritance (FR162): the index's `is_implementation` relationships become `overrides` (member to member), `implements` (a type to an interface or trait) and `inherits` (a type to another type). A target outside the repository is `resolved_external`: an `implements` when the index records its kind as an interface or trait, else an `inherits` with `detail.kind` `unknown`.
- Imports (FR163): each import statement the syntax tier reads is resolved through the index's occurrence of the package or type it names, to the file that holds the package's lowest-path definition, or to `<ecosystem>:<package>` (Go's standard library is `go:std`); a statement with no occurrence is `unresolved`, and the file's `imports` is `partial`. The occurrences inside the statement stay `references` rows. Where the syntax tier lacks the language, or cannot be reached, `resolved_calls` and `imports` are `unsupported`; the files of a batch it does not answer in time are `partial` (FR170).
- Memory (FR164): the index is read a document at a time and only each routed document's definitions stay in memory, so memory grows with the number of definitions, not the size of the index. `proofmesh scip add` reads it the same way. The metadata must come before the documents, as every indexer writes it. A length that no file could hold is refused before a buffer is made, and a document read again after the index file changed is refused. A test indexes a 1 GB index of 100,000 definitions with the adapter's peak resident memory under 600 MB (about 415 MB measured, with the syntax tier it starts); the reader reuses one buffer rather than allocating one per document, and the syntax tier is asked for spans 20 files at a time (FR531).
- Staleness: Proofmesh records each covered file's content when the index is named. A file edited after that, or every file of an index whose own file changed, goes back to its usual adapter, and its disposition says `scip_stale:<name>` until the person produces the index again and names it again.

### Running a pinned indexer (A38)

For a repository trusted with `proofmesh repo trust <repository> --build-evaluation`, `proofmesh scip run <repository> [--language L] [--container IMAGE@sha256:...] [--module-cache DIR] [--timeout S] [--max-memory MB]` runs the indexer for the language (scip-go for Go, scip-java for Java, Kotlin and Scala, rust-analyzer for Rust with build scripts and procedural macros off) and names the result. Without the grant it refuses with `TRUST_REQUIRED`, prints the grant command and the indexer command you could run yourself, and runs nothing; no MCP tool can start a run.

- The indexer must be installed (Proofmesh never downloads one; a missing one fails with the install command) and must report the pinned version: scip-go v0.2.9, scip-java v0.13.2, rust-analyzer 2026-11-09 (releases at least two weeks old). The table records, per platform, the release asset to install from and the sha256 GitHub publishes for it (an archive, so not the executable's own digest). The executable's own sha256 is recorded in the index and in snapshot identity; to enforce one, pin it in `<data dir>/indexers.json`: `{"scip-go": {"version": "v0.2.9", "sha256": "<hex>"}}`.
- It runs on a disposable copy of the current snapshot, so the working tree is untouched, with no shell, an allowlisted environment (`PATH`, a private `HOME`, the indexer's offline settings), dependencies read only from the module cache (default `<data dir>/module-cache`), a time limit (`--timeout`, default 1800 s) and a memory limit (`--max-memory`, default 4096 MB) that stop it with SIGKILL, and its output capped. A stopped or failed run's partial output is discarded and never named. A container run is named, and a timeout removes the container by name. An index.scip that is not a regular file, or is over 2 GiB, is refused unread. Each run has its own copy, log and index file.
- Without `--container` the run is a plain process: network and filesystem policy are not enforced, and the command says so. With `--container` (an image pinned by digest that holds the indexer) it runs with `--network none` and the cache read-only.
- The index records the indexer, version, the executable's own sha256, grant and isolation (`proofmesh scip list`). Facts from it carry analysis mode `trusted_build`, shown as for any build evaluation. After `proofmesh repo untrust`, the index is not read: its files return to their usual tier with unchanged keys, and the census gives `scip_revoked:<index>:<grant>` as the reason.

## Test recognition (FR191 to FR200)

Test code is recognised in two ways, and a symbol is decided on its own: by the **file convention** of its language, and by the **marker** its test framework puts in code. `find_symbols` and `get_relationships` with `include_tests` false, `find_tests`, test reach and `impact_completeness` all use the per-symbol decision, so a Rust `#[cfg(test)]` module in a source file is test code and the production code beside it is not.

- Go. Files: `_test.go` only; a directory named `test` holds packages like any other, and the package clause (`x_test`) does not matter. Entry points: a function `Test*`, `Benchmark*` or `Fuzz*` (no lower-case letter after the prefix) with one `*testing.T`, `*testing.B` or `*testing.F` parameter, or an `Example*` function with none; in a `_test.go` file only. A method and `TestMain` are no tests.
- Rust. Files: none: tests live in the source file. Entry points: `#[test]`, `#[tokio::test]` and any attribute ending in `::test`, `#[rstest]`. A `#[cfg(test)]` item and everything in it is test support, and so is every symbol of a file a parent declares as `#[cfg(test)] mod tests;` (`src/tests.rs`, `src/tests/mod.rs`), with the modules that file declares in turn.
- Python. Files: `test_*.py`, `*_test.py`, `conftest.py`. Entry points: in a test file, a function whose name starts with `test` (pytest's default prefix, so `testAdd` counts) and the `test` methods of a `Test` class; anywhere, the `test` methods of a `unittest.TestCase` subclass.
- Java. Files: `src/test/`. Entry points: `@Test`, `@ParameterizedTest`, `@RepeatedTest`, `@TestFactory`, `@TestTemplate` (JUnit, TestNG), and the `test` methods of a `TestCase` subclass (JUnit 3 style).
- Kotlin. Files: `src/test/`. Entry points: `@Test`, also under another name: `import org.junit.Test as T` makes `@T` one. An annotation imported from outside the known test frameworks is not.
- PHP. Files: `*Test.php`. Entry points: a method of a class extending a `TestCase` (see base classes below) that is named `test*`, tagged `@test` in its docblock or carries `#[Test]`.
- Ruby. Files: `_spec.rb`, `_test.rb`, `spec/`. Entry points: an RSpec `it`, `specify`, `example` or `scenario` block in a spec file (`_spec.rb`, `_test.rb`, a file under `spec/` or `test/`; the same call in `lib/` is an ordinary call of some DSL, with no role), and a `test_` method of a class whose base is `Minitest::Test`, `Test::Unit::TestCase`, `ActionDispatch::IntegrationTest`, `ApplicationSystemTestCase`, `ActiveSupport::TestCase` or any base whose name ends in `Test` or `TestCase`.
- C and C++. Files: `*_test.*`, `*_unittest.*`. Entry points: googletest `TEST`, `TEST_F`, `TEST_P` and the typed variants.
- Swift. Files: `Tests/`. Entry points: a `test*` method with no parameter of a class inheriting an `XCTestCase`, and a function marked `@Test`.
- C#. Files: `*Tests.cs`, `*.Tests` projects. Entry points: `[Fact]`, `[Theory]`, `[Test]`, `[TestCase]`, `[TestCaseSource]`, `[TestMethod]` and `[DataTestMethod]`, matched by name under any namespace. A type that holds one is test code wherever it sits, even outside a `*Tests.cs` file or a test project (before roles only the path and the project decided). Limitation: a `partial` class is read one file at a time, so a part that holds no test attribute is not marked test support when another part does.
- TypeScript and JavaScript. Files: `*.test.*`, `*.spec.*`, `tests/`, `__tests__/`, `spec/`. Entry points: none: a `test('name', fn)` callback is not a symbol.

A symbol carries optional `roles` (adapter protocol 1.1, snapshot format 0.9): `test` for an entry point, `test_support` for test code that is none, by its scope: the members of a `#[cfg(test)]` module, a class holding a test and the helpers of a test class. A symbol with neither has no `roles`. An adapter that sends none is as valid as before, and a snapshot sealed earlier has none, so it is decided by its path.

**Base classes.** A class is a test case when its base is one, or when its base chain reaches one through the repository, up to two bases: PHP `FooTest extends AbstractIntegrationTest` with that class extending `TestCase`, Python `class T(MyBase)` with `MyBase` a `unittest.TestCase`, JUnit 3 style Java and Kotlin, Ruby test bases. Bases are matched by simple name, so two classes of one name are both candidates. Where the chain leaves the repository (the base is a framework class the repository does not hold), a class named `*Test`, `*Tests` or `Test*` in a test file counts by convention; where the base is in the repository and is no test case, it does not. A chain longer than two bases is not followed.

`find_tests` lists only entry points in a file whose adapter sent roles (Go, Rust, Python, Java, Kotlin, PHP, Ruby, C, C++, Swift and C# with their markers): a helper that calls the subject is no test, but a test that calls the helper reaches the subject through it. In any other file (an adapter that sends no roles, a snapshot sealed before roles, TypeScript and JavaScript, a file of a marker language in which no symbol has a role) every symbol in test code is a test, as before. A block that declares no name is named by its call and its description, `it "adds"`, and a googletest macro as it is written, `TEST(Calc, Adds)`.

`find_tests` says when the subject's language has no resolved calls: `Calls in Go are not resolved yet`, and no test is listed as executing it, with `include_inferred` false; by default it follows Go and Java candidate calls (FR205), lists the tests it reaches that way as inferred, and says so instead, for a subject that has candidate call sites of its own. The markers are read from syntax alone, so no test framework needs to be installed.

## The language census

`workspace_status` returns `languages` and `proofmesh status` prints it, with no configuration (FR136 to FR141). Every discovered file is in exactly one row: the language by GitHub Linguist's name, a kind (`code`, `template`, `data`, `prose`), or `unknown` with its extension, or `binary`. Rows list code and template kinds first, then by file count, then by name.

- Detection uses the file name, the longest known extension (`.html.erb` is ERB, not HTML), the shebang of a file with no extension, and a content check for `.h` (C++ or Objective-C when the text says so, C otherwise). An extension several languages share and nothing settles, such as `.m`, `.pl` or `.v`, is `unknown` with the extension, never a guess. Comments and string literals are blanked before a header is read, and up to 64 KB of it is scanned, so a long licence banner does not hide C++. Only a short final suffix of letters and digits is an extension: files without one share one `(no extension)` row and files with an implausible one (`app.log.2024-11-24`) one `(other)` row, and past 64 rows the smallest are summed into a last `other` row, so the rows always sum to the inventory. An Objective-C header has its own row (no grammar, tier `none`) and is not given to the C parser. The names, kinds, extensions, file names and interpreters come from a trimmed copy of Linguist's `languages.yml` (MIT; `THIRD_PARTY_NOTICES.md` carries its notice), vendored as data in `packages/proofmesh/src/indexer/linguist-table.ts`.
- A file whose language only its shebang or content gives is routed to that language when the syntax tier reads it, so an extensionless bash script is Shell and its functions are symbols. A script in a language a semantic adapter reads, such as Python, still waits for its extension.
- `tier` is the tier that read most of the row's files: `precise:<adapter>`, `scip:<index>`, `syntax` or `none`, and `tiers` lists each with its file count. Each indexed source file records its tier as the `tier` key of its capabilities. Files left out by rule are counted under `excluded`, by rule, and are in no tier.
- `capabilities` counts the row's files at each level (`complete`, `partial`, `unsupported`, `failed`, `not_run`) for `symbols`, `imports`, `references` and `resolved_calls`; each capability's counts sum to `files`.
- `reason` says why the row's weakest files stop where they do (`no_precise_tier`, `no_grammar`, `not_code`, `adapter_unavailable:<id>`, `adapter_failed:<id>`, `scip_stale:<index>`, `scip_revoked:<index>:<grant>`, `unknown_language`, `binary`, `excluded`), and `remedy` is advice from the table below. The census runs nothing and installs nothing; a SCIP indexer runs only in a repository you trust.
