# Operations: index progress and jobs, indexing a commit, moving a repository, backup, restore, retention, client configuration

## Index progress and jobs

`proofmesh index` writes a progress line to stderr each time the phase changes, with done and total where they are known: `discover`, `capture`, `initialize` and `analyze` for each adapter, `write` (resolving and writing relationships, with progress every 25,000 of them), `check` (validating the snapshot, filling aggregates and planner statistics) and `seal`. While a phase runs it repeats the latest line every five seconds, so a long run is never silent; a running adapter's line adds its languages, files a second and an estimate of the time left (`analyze csharp 400/28000 (csharp: 6.2 files/s, about 74m left) (still running)`), and holds figures only, never source text. stdout keeps only the summary. The summary adds how long each phase took, the seconds per analysed file of each adapter, and the peak resident memory of each adapter process, sampled with `ps` every three seconds and once at the end. Where `ps` is missing the memory line is left out, and processes an adapter starts itself, such as build servers, are not counted.

Every index the CLI runs is an index job, requested by the operating-system user, like the jobs `request_index` starts. `proofmesh status` and `workspace_status` (in `data.jobs`) list the repository's jobs that are queued or running, with start time and phase, and `get_job` reads one. Before a repository has its first snapshot, a tool's `SNAPSHOT_UNAVAILABLE` refusal names the running job and its phase instead. A job is running only while its process holds the repository's index lock (`locks/index-<repository id>.lock` in the data directory, which records the pid, host and the process start time), so a job whose process crashed or was killed reads `interrupted` and is no longer listed. Indexes of different repositories run at the same time. A second index of a repository waits for the first (its job stays queued, with a heartbeat), or with `index --no-wait` exits `INDEX_IN_PROGRESS` naming the running pid and start time; a lock whose process is gone is taken over and the run says so. An index that fails because an adapter died keeps the facts of the batches that finished (in the fact cache and in the checkpoint), says how many, and the next `index` resumes from them; the previous snapshot stays current. `index --allow-partial` instead publishes what was analysed: the files the adapter did not reach are `failed` with `adapter_died`, the snapshot's meta `partial` and the job result name them, every answer from it carries a `partial:` limitation, and the next index asks the adapter again. `gc` and an index exclude each other. `PROOFMESH_BUSY_TIMEOUT_MS` is read only with `PROOFMESH_TEST_HARNESS` set.

A job records `progress_at`, the last time it reported progress, and `phase_started_at`; a running job reports at least every five seconds while an adapter analyses, and at least every five seconds in any other phase that can fire a timer (capture every thousand files), so a `progress_at` that stops moving means the run is stuck, not slow. `elapsed_ms` is the time since it started, or its whole run once finished. When analysis starts, `plan` says per adapter whether the run is `incremental` or `full`, how many files it re-analyses and how many replay cached facts. A finished job keeps the number of files indexed in `done` and `total`, and its result says how many files were reused and analysed. `get_job` reads the catalog, so it answers before the repository has a snapshot. While an adapter analyses, `adapters` holds, per adapter, the same figures the index prints: `language`, `done`, `total`, `files_per_second` and `eta_seconds` (null until a file is done), refreshed every five seconds; only adapters that are analysing now are listed, and `progress_at` moves on every tick in every phase.

## Adapter memory budgets

Each adapter process runs under a budget in MB of resident memory. Unless a setting names one, it is half of the machine's physical memory, at least 8192 and at most 32768: 24576 on a 48 GB machine, 8192 on 16 GB. The C# adapter compiles every project in one process and keeps the compilations, so about 30,000 files need an estimated 6 to 10 GB. The host enforces it four ways, and the enforcement is sampled, not kernel-enforced (macOS has no cgroups, and a Linux address-space limit is not reliable for Node or .NET): it sums the resident memory of the adapter's whole process group, so a Pyright or MSBuild child counts, with one bounded `ps` call every three seconds and stops one that passed the budget with SIGKILL; it takes the same sample at the end of every batch, before accepting its results, and rejects a batch that ended over budget; it starts Node adapters with `--max-old-space-size` and the C# adapter with `DOTNET_GCHeapHardLimit` set to the budget, and an adapter that exits 137, is killed by a SIGKILL the host did not send, or writes an out-of-memory message under a budget counts as having passed it. A spike that ends between two samples is seen only by the engine limits. A platform without `ps` has only the engine limits.

An adapter that passes its budget is started again with half the files of the batch that did it, and with batches of that size for the rest of the run, so no file fails for memory until a single file does. A file that passes the budget alone fails with `memory_budget`; every other file is analysed, and the language census counts the failed file. An adapter that passes its budget while loading the project, which is while starting or answering `workspace` and so before its first batch, fails all its files with `memory_budget` at once and is not started again: a smaller batch cannot shrink the load. The index then prints the load peak and the `repo config` command that raises the budget. The facts sealed under a budget are those of an index without one. The index prints each overrun, names it in the job's result (`memory_restarts`, also for an adapter that failed while starting or answering `workspace`, with its budget and peak), and the error names the adapter, the budget and the peak resident memory. Because a file failed under one budget is not the answer under a larger one, the budget is part of a snapshot's identity: raising it indexes again, and replays the cached facts of every file that did not fail.

Raise a budget for one repository and adapter with `proofmesh repo config <repository> --adapter <id> --memory-mb <n>` (it keeps the rest of that adapter's configuration), or for every adapter, the conformance kit and `proofmesh adapter check` with the environment variable `PROOFMESH_ADAPTER_MEMORY_MB` (a whole number of MB). A budget set too low for an adapter to start costs that adapter's files, so raise it when the run reports `memory_budget` for many files.

The index summary prints each adapter's budget and whether a setting or the machine chose it (`adapter memory budget csharp 24576 MB (half of this machine's memory, 8 to 32 GB)`), and `get_job` carries the same in the job's `plan` while it runs and in its `result` after.

## Index host heap

The process that runs `proofmesh index` holds every relationship in memory until the write, which extrapolates to about 5 GB at 30,000 C# files, above Node's default heap of about 4.2 GB on a 48 GB machine. `index` therefore starts itself again under `--max-old-space-size` from the same rule as the adapter budget (half of physical memory, 8192 to 32768 MB); `PROOFMESH_HOST_MEMORY_MB` (a whole number of MB) sets it instead, and the summary prints the heap. A host that runs out of heap fails with `BUDGET_EXCEEDED`, detail `host_out_of_memory`, naming `PROOFMESH_HOST_MEMORY_MB`, and its job is marked failed, rather than leaving a crash and a job that only later reads as interrupted. The outer process passes on SIGINT, SIGTERM and SIGHUP; if it is killed with SIGKILL its host is not.

## Synthetic large tier

`node bench/graph-bench/synthetic-large.mjs --projects N --files M [--out result.json] [--adapter <entry>]` generates N C# projects, each referencing the one before, holding M files in all, indexes them, and prints the peak resident memory of the index host and of the adapter beside the budget and heap in force. Run it by hand with the C# adapter built (for example `--projects 300 --files 30000`) to check the defaults against numbers; the tests run a three-project version with a stand-in adapter.

No time or size budget is promised before the large tier has measured one. Measured so far: the Python adapter took 41 s for 71 files of a public command-line library, about 0.6 s a file, so a 10,000-file Python repository takes more than an hour; a 6-file fixture took 0.41 s a file (the index summary's `adapter seconds per file` line gives the figure for any run). The owner sets time budgets from the large tier's first results.

## Large benchmark tier

`sh bench/graph-bench/run-large.sh [<clone-or-url> [<copy-dir>]]` indexes a pinned public repository of more than 20,000 source files in several languages (dotnet/aspnetcore at the commit named in the script, MIT licence) three times on an empty data directory, and edits one file for each run's incremental index. It writes `bench/graph-bench/out/large.md` and `large.json` with the median of the three runs for the cold index time, the peak memory of each adapter process, the store size, the time and files re-analysed for the edit and the seconds per file of each adapter, and the machine that ran it. It needs a machine of 16 GB or more and the .NET SDK, and is run by hand: it is not part of `pnpm test` or `run-all.sh`.

## Registered roots

`proofmesh repo add` and `repo list` warn on stderr when a root is under a temporary directory and may disappear, when it no longer exists, and when the registered name differs from the root's directory name; stdout keeps the id or the list. `proofmesh --version` prints the version.

## Indexing a commit

`proofmesh index <repository> --rev <commit-ish>` indexes a commit instead of the working tree. It resolves the name with `git rev-parse --verify <rev>^{commit}`, writes that commit's files into a private directory under the data directory's `staging/` through a temporary index file (`git read-tree`, then `git checkout-index --prefix`), indexes that directory, and deletes it afterwards, also when the index fails. Nothing is written to the registered working tree, its HEAD or its index, and none of its files is read, so uncommitted edits and untracked files stay out of the snapshot. Git LFS files are indexed as their pointer files, since fetching their content could reach the network; submodules are not included.

The snapshot keeps the registered repository's id and becomes current, because it is what the person asked for. Its `commit` is the resolved sha, its `ref` is the branch or tag the name pointed to (`detached` for a sha or an expression such as `HEAD~1`), and `behind_remote` counts how far that commit, not the working tree's HEAD, is behind the remote default branch. `proofmesh status` prints the commit. Strict freshness compares the snapshot with the working tree as always, so while the working tree is elsewhere a strict query is refused as stale and starts an index of the working tree, and `proofmesh watch` re-indexes the working tree on its next check. Installed packages and other external inputs are read from the registered working tree, as for any index.

With `--keep-current`, the repository's current snapshot stays the one it was before; when it had none, the commit's becomes current. `impact_completeness` indexes a commit this way, and so does `proofmesh completeness`, which indexes the head before the base. The index job's result names the commit, which is how a later query finds that commit's snapshot (FR109).

## Moving a repository

`proofmesh repo move <repository> <new-path>` re-roots a registration, for a checkout that moved or a second clone you want to index instead. The new path must be the top of a working tree of the same git repository: it shares the registered root's git directory (`git rev-parse --git-common-dir`), or, when the old root is gone or another clone is named, it holds the commit of the current snapshot. Otherwise the move is refused. The repository keeps its id, and with it its snapshots, notes, observations, SCIP indexes and workspaces. Build-evaluation trust does not move: it was granted for the old checkout, so the move revokes it, and a person grants it again for the new one. The old root can then be registered again with `proofmesh repo add`, as a new repository with another id.

## Backup and restore (FR050)

`proofmesh backup <dir>` copies the catalog through SQLite's online backup API, so it is consistent while a server or watcher runs, then every sealed snapshot, link file, evidence object and token, and writes `backup-manifest.json` with a sha256 per file. Staging files and temporary objects are not backed up.

`proofmesh restore <dir> --into <data-dir>` verifies every hash first and copies nothing if one fails; the target must be empty. The restored directory is a full data directory: queries answer from it at once.

## Retention and garbage collection (FR051)

`proofmesh gc [--keep N] [--dry-run]` keeps the newest N published snapshots per repository (default 3) and retires the rest, deleting their sealed files, then deletes evidence objects no remaining snapshot references. It never retires the current snapshot, a pinned one (`proofmesh snapshot pin <id>`), or a member of a recorded workspace link file, and it refuses to run while an index holds a lock; an index started while gc runs waits for it. `--dry-run` lists what would go. A retired snapshot keeps its catalog row, so its id still names what existed.

`--records-days D` (default 30) sets how long query records and session trails are kept. gc deletes the ones recorded more than D days ago. Before this option, query records were kept forever. `proofmesh trail purge [--session <id>]` deletes trails at any time (FR612).

## Client configuration (A13, FR041)

`proofmesh mcp-config [--client claude-code|codex] [--scope project|user]` prints the registration for this installation. It writes only when asked, and only a Claude Code `.mcp.json` (`--write .mcp.json`), keeping the other servers in it. `packages/proofmesh-plugin/` is the Claude Code plugin: a skill that sends agents to Proofmesh before searching by hand, and the MCP registration.

## Evaluation harness (A12)

`pnpm eval -- sessions <set.json> --repo <dir> --data-dir <dir> --out <dir> [--model M] [--budget-usd N]` runs one headless Claude Code session (`claude -p`, streamed output) per question in each of two conditions, in `<repo>`: with Read, Grep, Glob and the Proofmesh MCP tools over `<data-dir>`, and with Read, Grep and Glob only. With `--with-skill`, the first condition also gets the plugin's skill appended to its system prompt, as installing the plugin would give it; without it, an agent offered the tools on a small repository may never call them. Both conditions read no user-level settings, so no personal plugins or hooks run, take MCP servers only from the command line, and keep no session. Each session's own result supplies the answer, turns, tokens (input, cache and output) and the cost Claude Code reports; the stream supplies each tool call by name. The run writes `with.json`, `without.json` and `method.json` (agent version, model, times, isolation, correctness rule) to `<out>`, then scores them.

`pnpm eval -- <set.json> <with.json> <without.json>` scores two recorded sessions again, or sessions recorded some other way. A question is correct when every expected fact, or one of a fact's listed alternatives, appears in the answer, ignoring case: a proxy a reader can check by hand, not a judgment. The report holds only what the sessions recorded.

`bench/eval/samples/ts-invoicing-golden.json` is a public golden set for `fixtures/ts-invoicing`, written by hand from its source; measured runs on it are in `bench/results/eval-ts-invoicing-*`. A private set about a large private repository lives in the gitignored `eval/results/`. On a subscription sign-in, the reported cost is what the same tokens would cost on the API, not a charge.
