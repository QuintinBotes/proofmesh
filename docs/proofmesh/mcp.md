# The MCP service

Proofmesh serves its tools over MCP on stdio (`proofmesh mcp`) and over Streamable HTTP on loopback (`proofmesh mcp --http`). Both transports build the same server around the same query service, so a client sees the same tools, schemas and answers on either (FR034).

## Tool profiles (FR420 to FR423)

A client that does not defer tool loading puts every listed tool's name, description and input schema into the model's context before the first question. So `proofmesh mcp` lists only the `core` profile, whose `tools/list` stays under 20,000 bytes (a test asserts it; 19,758 bytes for 14 tools since `search_concepts` joined it, against 142,653 for all 45 with `get_cochanges`):

| Profile | Tools |
|---|---|
| `core` (default) | `find_symbols`, `get_symbol`, `get_symbols_at`, `get_relationships`, `trace_paths`, `analyze_impact`, `find_tests`, `search_sources`, `search_concepts`, `read_evidence`, `workspace_status`, `list_repositories`, `get_overview`, `list_queries` |
| `data` | `get_table_reach`, `get_property_reads`, `find_query_source`, `get_external_usage`, `get_session_trail`, `get_context_map` |
| `claims` | `verify_claim`, `get_claims`, `prepare_verification`, `get_verification` |
| `extra` | `list_snapshots`, `list_workspaces`, `get_ecosystem`, `compare_snapshots`, `impact_completeness`, `request_index`, `get_job`, `get_memory`, `save_memory`, `find_stale_mentions`, `find_unused`, `find_cycles`, `find_entry_points`, `find_hubs`, `plan_rename`, `plan_move`, `search_structure`, `get_symbol_card`, `query_graph`, `get_findings`, `get_cochanges` |

- `proofmesh mcp --tools core,data` (or any comma-separated list) lists those profiles; `--tools all` lists every tool exactly as its schema file declares it. Both transports take it. In a client configuration, put the option after `mcp` in the arguments, for example `"args": ["mcp", "--tools", "all"]` in `.mcp.json`. A client restarts the server to change profile.
- Outside `all`, a listed tool keeps its description and every field of its input schema, with types, enums, patterns, defaults and required fields, but not the per-field descriptions; `envelope` keeps its first sentence. The full schemas are `schemas/tools/<tool>.input.schema.json`, and the server validates every call against them whatever the profile.
- `list_queries` lists every tool with its `profile`, loaded or not, and says how to load the others.
- A call to a tool of a profile the server was not started with is `INVALID_ARGUMENT` with `details.profile` naming the profile, and the message says which `--tools` option loads it.

## Concept search (FR580 to FR585)

`search_concepts` takes a description, such as an issue or a task in prose, and ranks the symbols and files that match it, with no model and no network. It is in the `core` profile: finding where to start is the first step of most tasks, and without it an agent falls back to many `search_sources` calls.

```
# search_concepts · 6 rows · snap_3dc3206b273ef32924950c3d current
RelationLoader.load src/query-builder/RelationLoader.ts:26 method score=24.048 terms=loader,relation,relationloader via=RelationLoader.enableLazyLoad
RelationLoader.enableLazyLoad src/query-builder/RelationLoader.ts:386 method score=23.706 terms=lazy,relationloader,loader,relation
RelationLoader src/query-builder/RelationLoader.ts:12 class score=21.592 terms=relationloader,relation,loader,lazy
src/query-builder/RelationLoader.ts:26 file score=46.593 terms=relationloader,loader,relation,lazy
src/metadata/RelationMetadata.ts:19 file score=29.295 terms=relation,lazy
src/query-builder/RelationIdLoader.ts:12 file score=28.601 terms=relation,loader,relationloader
```

That is `lazy relation loader` asked of TypeORM 0.3.20's `src/` (the parity fixture of `bench/parity`), cut to three rows of each.

- **The index (FR581).** Each snapshot (format 0.13) holds, for every indexed file, its terms and the lines each occurs on: the words of every identifier, split at camelCase, PascalCase and snake_case boundaries and lower-cased, plus a multi-word identifier whole, its words joined (`RelationLoader` and `relation_loader` are both `relation`, `loader` and `relationloader`); the words of comments, docstrings and string literals, which are words of the text alike; and the segments of the file's path, on line 0. Stop words of English prose, single letters and numbers are left out. It is filled when the snapshot is sealed, from the captured text, whatever adapter read the file. A snapshot sealed before format 0.13 has none, and the answer says to index again. The extraction has its own version in the snapshot identity, so changing it rebuilds the next index.
- **Query terms (FR584).** The text is split the same way, and each run of two or three adjacent words is also a term joined, as the index holds a multi-word identifier (`lazy relation loader` asks for `relationloader` and `lazyrelationloader` too). A light stemmer, the same for every language, lets a term of at least four letters also match the index terms it differs from by an ending of up to three letters (`loader` matches `load`, `loads` and `loaded`); a term and its variants count as one. Each term the index holds is weighed `(1 + ln tf_q) × idf`, with `idf = ln(1 + (N − df + 0.5) / (df + 0.5))` over the `N` indexed files, so an identifier common in the repository (`get`, `data`, `value`) counts for little; `df` counts the files holding the term or a variant. The 32 heaviest are kept; when a text has more, `terms_dropped` and a limitation say how many were left out. A text none of whose words the index holds answers no rows and the limitation `no indexed term matched` (FR583).
- **Files.** `file = Σ w_t × (bm25(tf, len) + path_t) + best symbol`, where `bm25(n, len) = n (k1 + 1) / (n + k1 (1 − b + b len / avg_len))` with `k1 = 1.2` and `b = 0.75`, `tf` counts the term's occurrences in the file, `len` the file's occurrences of all terms, and `path_t` is 1 when the term is a word of the path.
- **Symbols.** For each symbol of the 200 best files: `symbol = Σ w_t × (bm25(n, len) + name_t)`, where `n` counts the term's occurrences inside the symbol's span, `len` is its declaration's token count (with an average of 120), and `name_t` is 2 when the term, or a variant, is a word of the symbol's own name and 0.5 when it is a word of its container's (`RelationLoader` in `RelationLoader.load`).
- **Graph proximity (FR582).** From each of the five best symbols (the seeds, which gain nothing from each other), the walk follows resolved `calls`, `inherits`, `implements`, `overrides` and `references` either way: a symbol one relationship away gains half of that seed's score and one two away a quarter, the largest such gain once, and names the seed in `via`. The gain is bounded by its seed, so proximity orders the neighbours of strong matches and never outranks a lexical match on its own.
- **Order.** Production code first, then test code (recognised as `find_symbols` recognises it), unless `include_tests` is true; then by score, then by path, line and id, so the same snapshot and text always answer the same rows. Files flagged generated are left out; vendored files are not indexed.
- **Rows.** 20 symbols and 20 files unless `max_rows` says otherwise. A lean symbol row is `<name> <path>:<line> <kind> score=<n> terms=<a,b>` (at most five terms, the heaviest contribution first) and `via=<name>` when proximity raised it; a file row is `<path>:<line> file` with the same tags, its line the declaration of its best symbol. `kinds` and `path_prefix` narrow the rows.
- **How well it does.** `bench/localise` asks it the problem statement of 50 pinned SWE-bench Lite instances and scores file Acc@5 and function Acc@10 against a BM25 baseline computed by the same harness (its README states the latest results and how to run it).

## Read, management and execution (FR036)

`list_queries` gives every tool a `capability`:

- `read` tools answer from snapshots and the catalog. They record that they answered, as a query record or a claim's verification run, and start nothing.
- `management` tools ask the workspace to start or keep something: `request_index` starts an index job (as `impact_completeness` does for a side with no snapshot yet), `save_memory` saves a note proposal that a person accepts later, and `prepare_verification` prepares a plan that a person approves.
- `execution` runs repository code. No tool has it. A person approves and runs a verification with `proofmesh verification approve` and `proofmesh verification run`, and only the CLI loads the launcher.

## Schemas and the contract manifest (FR037)

Every input is validated against `schemas/tools/<tool>.input.schema.json` before the tool runs. Every answer is validated against `schemas/envelope.schema.json` and `schemas/tools/<tool>.data.schema.json` before it is sent. An answer that fails is a defect, so the client receives `INTERNAL_ERROR` naming the first mismatch instead of the answer.

`list_queries` returns `contract`, the version of each public contract: the envelope, the snapshot format, the link format, the adapter protocol, the bundle format and the newest catalog migration. [COMPATIBILITY.md](../../COMPATIBILITY.md) states the policy for each.

## Deadlines, bounds, errors and cancellation (FR038)

Each call takes `limits` for time, rows, bytes and depth, clamped to the server maximum, and an answer cut short by one says so in `completion`. Errors are tool results with `isError` and a body that matches `schemas/error.schema.json`.

Cancellation has a limit. Queries run synchronously against SQLite, so the server reads a cancellation only between calls:

- A call cancelled before its handler starts is not run. As MCP requires, it gets no reply. In process, the query service refuses such a call with `CANCELLED`.
- A call that is already running finishes, or stops at its deadline (`timeout_ms`, at most 30 s), and its answer is sent. The cancellation arrives too late to stop it.
- Over Streamable HTTP the server is stateless: each POST gets a fresh server, so a cancellation, which arrives in a POST of its own, cannot reach a call in flight. The call runs to its answer or its deadline.

## Relationship basis (FR181 to FR190)

Every relationship row `get_relationships` answers, and every dependent, test and path hop reached through relationships, carries `basis`: `observed` when a compiler, an index or a declared configuration proves the relationship, `inferred` when a convention, a name match or a contract match suggests it. It is derived when the answer is built, not stored: a row is `inferred` when its resolution is `candidate` or `ambiguous`, its origin is `contract_match`, `documentation` or `model_hypothesis`, or its `detail.inferred` is set. `resolved_external` rows are observed. An unresolved boundary is no relationship and has no `basis`.

A row reached through a chain is `inferred` when any hop of its strongest chain is. The strongest chain is the shortest all-observed chain where one exists: a dependent that an observed and an inferred chain both reach is `observed`, and `analyze_impact` gives the depth of that observed chain. A `trace_paths` path is `inferred` when any hop is, and each hop says its own `basis` in `relationships`. `get_relationships`, `analyze_impact`, `find_tests` and `impact_completeness` give `totals.by_basis` (`observed` and `inferred`). Check inferred rows before acting on them. `by_basis` counts rows that have a basis, so an unresolved boundary, which has none, is left out and the two counts can sum to less than the number of rows (`totals.in` and `totals.out` in `get_relationships` count every row). A `get_table_reach` reach row carries `basis` too: `inferred` when a hop of the chain from the endpoint or job to the table is.

## Reach through candidate edges (FR201 to FR210, FR560, FR561)

Where no compiler or index analysed a subject (Go and Java without a SCIP index), its calls are `candidate` or `ambiguous` rows, which are not edges. `analyze_impact`, `find_tests`, `trace_paths` and `impact_completeness` take `include_inferred`: `true` follows them, `false` never does, and `auto`, the default, follows them when every subject's file was analysed by the syntax tier alone (for `impact_completeness`, per changed symbol). Following walks a `candidate` site and an `ambiguous` site of at most five candidates, never one whose candidates were capped, and labels every row reached through one `inferred`; a row an observed chain also reaches stays `observed` (FR184). Auto is decided once, from the subjects: once on, the walk follows candidate sites in every file it reaches, a precise-tier file included, and the answer says so; a precise-tier subject follows none even where its walk meets a syntax-tier file. Answers for TypeScript, Python, C# and any SCIP-covered file, or a file that records no tier, are byte-identical with the default input, including where candidate sites exist. The answer says in `limitations` that candidate edges were followed and why, and how many ambiguous sites of more than five candidates it stopped at; it counts the candidate sites it did not follow only when `include_inferred` is `false`. `find_tests` keeps its own count when it does not follow them, by default for a precise-tier subject as with `false`: `<n> call sites with no single resolved target name code on these paths as a candidate; ...` (FR560). `impact_completeness` says these sentences once for all its changed symbols, summing their sites (FR561). The node budget is checked as each row is reached. Candidate imports are not followed.

## The context map (FR920 to FR924)

`get_context_map` (the `data` profile, lean by default) answers, within a byte budget, the declarations around a focus in both directions: what calls, implements, imports, references or tests it, and what it calls, implements, imports and references. It is the orientation call before a change; the precise tools answer the questions it raises. It is in `data`, not `core`, so the default `tools/list` keeps its room under 20,000 bytes; the plugin's registration loads `data`.

- `focus` takes `paths` (repository-relative files), `symbols` (a row name such as `Driver.escape`, a plain name, which may name several symbols, or an id), or `base` with an optional `head`: the declarations the diff from `base` to `head`, or to the working tree, changed on this snapshot, which are rows of their own, `changed` at depth 0. A declaration that only lost lines is placed by the head line at the gap. A deleted declaration is not on the snapshot and is not in the focus. When the snapshot is not of `head` (or of the working tree), a limitation says changed lines may fall on other declarations.
- `budget_bytes` (default 4,096, at most 65,536) is the answer's `max_bytes`: header, rows, limitations and the cursor line included, as for every tool (FR330). A budget too small for the header, one row and the cursor line is refused with `max_bytes_too_small`. `max_depth` (default 2, at most 4) is the hops from the focus. The rest of the map is a cursor away; `limits.max_rows` (default 100) also bounds a page.
- A row is `<name> <path>:<line> <relation> depth=<n>`, at the declaration; a file, and its module, is one row, `<path>:1`. The relation is the row's to the focus: `calls`, `implements`, `references` and `imports` for what the focus uses; `called_by`, `implemented_by`, `referenced_by` and `imported_by` for what uses it, or `tests` when that code is test code (recognised as `find_tests` recognises it). Relationships followed: resolved `calls`, `references`, `imports`, `implements`, `overrides` and `inherits` (the last two read as `implements`), calls and references to a member a reached symbol implements or overrides (dispatch), and candidate edges. A row ends ` inferred` when any hop of its strongest chain is a candidate edge or otherwise inferred (FR184).
- Each declaration is one row, at its least depth and, there, its strongest relation. Nothing in a focus file is a row.
- The rank, which two calls repeat exactly:
  1. by depth (`changed` rows at 0 first), and at a depth observed rows before inferred ones;
  2. within those, a file's first row before any file's second, and so on, so the map names as many places as the budget holds;
  3. within that, a row the focus uses and a row that uses it alternate, each side ordered by relation strength (`implements`/`implemented_by`, `calls`/`called_by`, `tests`, `references`/`referenced_by`, `imports`/`imported_by`), then the weight of the row's file (its relationships to the code one hop nearer the focus, every site counted), the row's own weight, path, line and name.
- A focus file no adapter analyses has an empty map, and the limitation names its disposition; a path that is no file of the snapshot is refused, as for every tool.
- On the parity fixture (`bench/parity`, TypeORM) with each question's target file as the focus, a 4,096-byte map names on average 62% of the truth's inbound files and 81% of the target's imports, where aider's 1,024-token map names 1% and 47% (0 to 8% per question); at 16,384 bytes the map names 89% and 100%, aider's 4,096-token map 3% and 68%. `sh bench/parity/run.sh` reports both at 4,096 and 16,384 bytes beside aider's 1k and 4k maps (FR924).

## Envelopes: lean, compact and full (FR095 to FR100)

The query tools whose results are code locations (`find_symbols`, `search_concepts`, `get_symbol`, `get_relationships`, `trace_paths`, `analyze_impact` and `find_tests`) answer in the lean envelope by default over MCP. A lean answer is plain text, with no JSON and no `structuredContent`:

```
# get_relationships · 1 row · snap_4f0c2a9b1d3e5f7a current
service src/service.ts:4
```

- The header names the tool, the row count and the snapshot. It says `current` when the snapshot is the repository's current one, and `stale` when it is older (pinned by `snapshot_id` or a cursor); a stale answer is still given, with a limitation naming the current snapshot.
- Each row is `<name> <path>:<line>`, then tags: `in` or `out` when both directions are asked, `depth=<n>`, `dispatch`, `external`, `candidate`, `ambiguous`, `unresolved:<reason>`, and the relationship type when a query mixes types. A row whose relationship is inferred ends with the token `inferred` (FR186). The name is the qualified name without its module prefix (`BudgetLedger.consume`); a file or module row is `<path>:<line>` alone; a name or path with a space, a quote or `#` is quoted as JSON.
- The line is the call, import or reference site for relationship, impact and path rows (one row per site) and the declaration for symbol rows. A `trace_paths` answer lists the hops in order, each at its call to the next, then the target at its declaration.
- A `find_tests` row is the test at its first call toward the subject, with `depth=<n>` (1 for a direct call), tagged `dispatch` or `reference` when that is how it reaches the subject; a test file that only imports the subject is `<path>:<line> import_only`, at the import (FR101).
- Test code is recognised by file convention and by each symbol's roles (FR191 to FR194, see `languages.md`): `include_tests` false leaves out a symbol that is test code by either, and `find_tests` lists a test entry point where the language marks them, any symbol in test code where it does not. When the subject's language has no resolved calls it says so, and lists no test as executing it (FR199).
- `impact_completeness` answers in JSON by default and lean when asked; `proofmesh completeness` prints its lean text. A lean row is `changed <name> <path>:<line> <added|modified|deleted> <status>`, and each dependent below it `  <relation> <name> <path>:<line> <status>`, the line being the site; a status is `changed`, `neither` or `tested: <test> <path>:<line> <evidence> depth=<n>`. A `# summary:` line follows the rows. While a side has no snapshot the answer is `pending`, with no rows: call `get_job` with its job id, then ask again (FR108 to FR113).
- `get_symbol` answers `stable_key` and `body_hash` (a lean row ends `stable_key=<key> body_hash=<64 hex>`): the hash of the declaration text with line endings, common indentation, trailing whitespace and the symbol's own name normalised, so it survives a move and a rename and changes with an edit (FR130, FR131). A snapshot sealed before hashes existed answers null and says to index again (FR135). A symbol the SCIP importer declared also carries `detail.scip`, the index's own symbol (FR441).
- A symbol can be named by its `stable_key` in place of its id: `key` on `get_symbol`, `get_relationships`, `analyze_impact`, `find_tests` and `get_memory`, `source_key` and `target_key` on `trace_paths` (FR149). A key is unique in a snapshot and the same whichever tier analysed the file (FR146 to FR148); an unknown key is `NOT_FOUND` naming it. `get_memory` lists a note reference matching several symbols under `ambiguous_refs` and reports `tier_changed` when only a file's tier changed (FR150).
- Every structured row that names a symbol carries its `stable_key` as `key` (`from_key`, `symbol_key`, `source_key` and `target_key` where the row has its own `key` or names a second symbol), so it can be passed back as the subject of the next call: relationships, impact, tests and their chains, paths, symbol lists, hubs, table reach, property reads, query-source candidates, completeness and ecosystem samples. A row whose id is no symbol carries none (FR280 to FR289). `trace_paths` explored edges and `get_overview` links carry `from_key` and `to_key` for each end that is a symbol (FR440).
- `compare_snapshots` lists a removed and an added symbol of equal kind and hash as `paired` (`moved`, `renamed` or `moved_renamed`, each with both ids and keys), any other match as `ambiguous` with its candidates, never a body of fewer than 10 tokens (counted in `counts.too_small`, with a limitation), and never a symbol with no hash. A module is its file's text, so moving one function out of a file shows the old module as changed (its range) and the new file's module as added; a module pairs only when a whole file moves unchanged, and a changed symbol with `body` among `what` when its hash differs, with the ids of both sides (FR132 to FR134).
- Markdown docs link to the code they name (FR820 to FR826). A `.md` or `.markdown` file no adapter reads stays `unsupported`, but its text is kept: each inline code span and each link outside a fenced code block that names a repository file (a link from the doc's directory, inline code from the root and then the doc's directory), a symbol by `Container.member` (`.`, `::` or `#`), a function or method by `name()`, or a class, interface, struct, enum, type alias or namespace by its bare name, is a `mentions` relationship from the doc at that line, origin `documentation` and so always `inferred`. A name of several symbols is `ambiguous` with up to five candidates, never guessed; a bare member or function name (`id`, `filter`) and anything that names no code is not recorded. `get_relationships` with `types: ["mentions"]`, inbound, lists the docs that name a symbol or a file. When the previous snapshot resolved a mention that names nothing now, the new snapshot records it as stale: `renamed`, `moved` or `moved_renamed` with the new name when `compare_snapshots` would pair the symbol, a file `moved` when one added file has its content, else `deleted` (a symbol whose file failed this time is not reported); it stays stale until the doc is fixed. `find_stale_mentions` (`extra` profile, optional `path_prefix`) lists them as `{ path, line, mention, change, to }`, and `workspace_status` counts them under `doc_mentions` with `resolved` and `ambiguous`. A doc's content is part of snapshot identity, so editing only a doc indexes again. Limits: an indented code block is read as text; other doc formats are not read; a doc flagged generated, by a marker or by `linguist-generated` in `.gitattributes`, names nothing; a doc that was moved loses its stale mentions.
- `plan_rename` (`extra` profile, FR980 to FR988) is a read-only rename plan: `subject_id` (or `{ name, path }`, or `key`) and `new_name`, answered with every site the rename must change, one row per `path` and `line` with its `kind`, `basis` and the `key` of the symbol named there. It changes no file. Code sites are `observed`: the declaration's name line, each resolved call and reference at the line that writes the name (a `super(...)` call or a call through an import alias writes another name and is no site), each import and export specifier of a top-level symbol through every re-export (`export { x } from`, `export * from`, a local `export { x }`), an export under another name (`export { x as y }`) and that name's own uses after it, a shorthand destructuring (`const { escape } = driver`) and its local's uses, and the symbol's own name in its own body (a recursive call). On the ten pinned symbols of the parity fixture these are exactly the TypeScript language service's `findRenameLocations` (default options). `must_rename_together` lists each member that implements or overrides the subject, or that it implements or overrides, at any distance, with its line; each one's sites are rows too. Seams are `inferred`, each with `seam` and `rule`, to review before changing: `doc_mention` (a doc's `mentions`), `route` (an OpenAPI `operationId`, an MVC conventional route), `rpc` (a gRPC server method), `graphql` (a resolver map field), `ffi` (either side of an FFI binding), `serialised_key` (a string literal that is exactly the name, in `[...]` or as a quoted object key) and `di_key` (such a string as an argument of `register`, `bind`, `provide`, `inject`, `resolve` and the like, or of a call that also passes the symbol). A string anywhere else, such as a log message, is not listed. `possibly_affected` lists apart the calls that did not resolve and call the same name, and calls resolved to several candidates among them the symbol, with their count in `counts` and a limitation. A symbol exported from a package's public entry (a `package.json` `main`, `module`, `types` or `exports` target, or the source a build emits it from) carries the limitation `public export: consumers outside this repository are not listed`, unless `include_workspace: true` is given in a linked workspace: then the calls and references of the other members that reach it through a package this repository builds (FR902) are sites with their `repository`, observed when the installed version is the built one (their import specifiers are not listed). A symbol of the scope of the subject, or of a member renamed with it, that already has `new_name` is named in a limitation. Limits: a seam is listed only where a rule or a string names it, so a name built at run time is not found; TypeScript data properties are not symbols, so they cannot be the subject; references other than calls and imports are recorded only where an adapter supports them (TypeScript, C#, and Python for classes and functions), each at every site; a call the syntax tier binds by name only is `possibly_affected`, and its other uses are not recorded; a call to the symbol inside its own body is found by its spelling, so a parameter of the same name that shadows it is taken for it; a re-export of another module's symbol of the same name through the same barrel is not told apart; a string key is read on its own line, so a call split over lines is not seen; an import alias that a file exports is followed into that file only, not on through files that re-export the alias.
- `plan_move` (`extra` profile, FR1280 to FR1285) is a read-only move plan: `path` (a file) or `subject_id` (or `{ name, path }`, or `key`: a top-level symbol), and `to_path`, answered with every site the move must change, one row per `path` and `line` with its `kind` and `basis`, and for an import its `specifier` as written and its `new_specifier` in the same style (no extension, a `.js` for a `.ts`, a directory for its `index`, a dotted Python module). It changes no file; apply each `new_specifier` at its line, then move the code. A file move lists as `observed` every statement elsewhere that imports or re-exports the file (`import`, `export`, a dynamic `import()`) and the file's own imports whose relative specifier its new place changes; and as `inferred` seams, to review, a string literal in a captured file that names its path from that file's directory or from the root (`seam` `path`, such as a `package.json` `exports` target or a mock registry's module) and a doc's link or inline code that names it (`doc_mention`). A file move onto an existing path is refused. A symbol move lists the statements that import it by name or re-export its file (`split: true` when the statement names other things that stay, as `export *` does), the first use of it elsewhere in its old file (`add_import`, with the specifier to import it by), and the first use inside it of each top-level declaration outside it (`dependency`, with `name` and the specifier its new file imports it by). A public entry that is or re-exports the file carries `public export: consumers outside this repository are not listed`. Limits: a specifier written through a path alias, a package name or a relative Python import has no `new_specifier`, and a limitation counts them; a new import is written without an extension; a file no adapter reads (a JSON or YAML config other than a build manifest) is not captured, so a path in it is not listed; a namespace import (`import * as m`) that reaches a moved symbol, the imports of packages a moved symbol uses, and whether a dependency is exported from the old file are not listed; a C# move changes no import, so its plan lists only what other languages name.
- `get_symbol_card` (`extra` profile, FR1180 to FR1182) answers in one read-only request what Observatory's Proof lens shows for a symbol (`symbol_id`, `{ name, path }` or `key`): the symbol, its `declaration` evidence (span, hash, extractor, analysis mode, integrity and text), and `incoming` and `outgoing`, each `{ rows, total, next_offset }`. A row is a `get_relationships` row (`types`, default `calls`, with external targets included) plus `evidence`: its call site's span and integrity, and `context`, the whole lines of the site (at most 8) with the cited span's character offsets as `highlight`, or `null` when the object fails its integrity check or is missing. `limits.max_rows` applies to each side and `max_bytes` to the whole answer, cutting rows from the end of each side; pass `direction` (`in` or `out`) and that side's `next_offset` as `offset` for the next rows. It answers JSON, not lean rows. `trace_paths` gives each hop of a path its call site, `relationships[<assertion>].site` (FR1185).
- `get_symbols_at` takes `locations`, 1 to 100 of `path:line` (a column is ignored), and answers one row per location, in order: `<location> <name> <path>:<line> <kind>` for the innermost symbol holding the line (the file's module when no inner symbol does), or `<location> - <reason>` with `not_indexed`, `no_symbol`, `not_found` or `line_out_of_range` (FR119, FR123). Envelope `full` adds each symbol's id, `stable_key` and `tier` (`precise`, `syntax` or `scip`) (FR120).
- `get_session_trail` (the `data` profile, FR610 to FR615) answers lean by default too. It takes `session_id`, Claude Code's session id, and returns what the Proofmesh plugin recorded for that session in this repository. Rows come in two groups. First, one row per entry, in order: `<seq> <kind> <tool> <path or symbol id>`, tagged `failed` when the call failed or was denied, and `agent=<id>` for a subagent's call. Second, for each symbol declared in a file the session changed, a row `<name> <path>:<line> changed`, followed by its `analyze_impact` dependents that no successful `opened` entry names. Each dependent is tagged `never_seen`, or `searched_only` when a search named a path above it, plus `depth=<n>`. A dependent's line is the site that reaches the change. A search of the whole repository (`.`) covers no file, since the trail keeps no matches. Recording is off until a person runs `proofmesh trail on <repo>`. The trail holds ids and repository-relative paths only, never source text or search patterns. `proofmesh trail purge` deletes trails, and so does `proofmesh gc` once they are older than `--records-days` (default 30). A limitation says when recording is off, when the trail was cut at 10,000 entries, and when the snapshot predates the session's last change.
- While recording is on, `proofmesh mcp` also keeps the subjects of each query it answers, grouped by the session id it holds for the connection (`mcp_...`; one per stdio connection, one per `--http` process), and `list_queries` names a recorded query's `session_id` (FR1940 to FR1945, #50). `get_session_trail` with that id lists them as entries, one a subject, each with its `query_id` and `snapshot_id`: a search's subjects are the symbols on the page it returned (`searched`), a `compare_snapshots` diff's the base side of each removed and changed symbol (`changed`), a `verify_claim`'s its source and target (`claimed`), and any other query's the symbols its input names (`opened`). A symbol of another snapshot is matched by its stable key; a changed symbol the answering snapshot does not hold is named in a limitation with the `snapshot_id` to pass. Subjects are symbol ids and repository-relative paths the snapshot holds, never source text or a query's words; they go with their query records under `gc --records-days` and with `proofmesh trail purge`.
- `find_unused`, `find_cycles`, `find_entry_points` and `find_hubs` (the `extra` profile, FR940 to FR946) answer lean by default too, and take files by `path_prefix`:
  - `find_unused` rows are `<name> <path>:<line> <kind>` tagged `unused`, `reachable_only_by=test|framework|public_export`, or `possibly_used sites=<n>` (and `inferred` when a candidate edge names it), unused first. Defaults: kinds function, class, interface, type alias, enum and variable, top-level only, test code neither checked nor counted as a user. A symbol nothing reaches through a resolved relationship is unused; one only tests, a framework route, job, handler or registration, or a package's public exports (`package.json` `main`, `module`, `types`, `exports` and what they re-export) reach is listed apart; one an unresolved call by its name or an inferred edge could reach is `possibly_used`. `kinds: ["module"]` checks files.
  - `find_cycles` rows are `<imported file> <importing file>:<line> cycle=<n>`, one per pair of files that import inside each strongly connected set, at the first import's line, tagged with the import kind when not static (`re_export`, `type_only`, `dynamic`) and `inferred`. Runtime cycles come first; a set that is strongly connected only when type-only imports count is a separate cycle, `type_only`, listing only the imports no runtime cycle inside it already lists. Pass `include_type_only: false` for runtime cycles alone.
  - `find_entry_points` rows are `<path>:1 not_imported` for each module no file under the prefix imports, then `<name> <path>:<line> endpoint|job`, then the files `package.json` names (`main`, `bin`, `exports`), or the manifest's line with the path as written and `not_indexed` when no indexed file matches.
  - `find_hubs` rows are `<name> <path>:<line> <kind> fan_in=<n> fan_out=<n>`, the `top` (default 10) by `fan_in` (distinct symbols that use it), `fan_out` or `betweenness` (sampled from at most 1,000 sources on a larger graph, which a limitation says).
  - `find_unused`, `find_cycles` and `find_entry_points` page with a cursor; their totals count the whole answer. `find_unused`, `find_entry_points` and `find_hubs` leave generated files out unless `include_generated: true`, and say how many they left out (FR299). `path_prefix` is case-sensitive.
- After the rows come `# ` lines: the limitations of this answer, then `# more: cursor <c>` when there is a next page. Pass `<c>` as `cursor` to continue.
- Ids stay available: `find_symbols` with `include_ids: true` ends each row with `id=<symbol id>`, and every symbol id parameter also takes `{ "name": ..., "path": ... }`, the name as a row shows it (or the plain name), unique in the file that declares it. An outbound `get_relationships` row's path is its call site, not the callee's file. An ambiguous name is refused with `INVALID_ARGUMENT`, listing the candidates as rows with their ids.

`compact` and `full` stay selectable by name, and only they send `structuredContent`: `full` is the whole envelope, and `compact` leaves out what an earlier answer from the same snapshot gave (coverage, unresolved reasons, standing limitations, requested limits). The other tools answer in JSON as before: the first answer per snapshot on a connection is full and later ones are compact. In process and over the HTTP API, the default envelope stays `full`.

A JSON `analyze_impact` row holds everything its lean row shows, so a client never parses the text (FR860 to FR862, #159). Beside its `id`, each dependent carries `line` and `relationship`. `relationship` is the type of the relationship that first reached the dependent, or `dispatch` when it was reached only as an implementation or override of a member the walk reached. `line` is where that relationship sits in the row's `path` (for a call, the call site), or the declaration line when dispatch alone reached it. When the relationship is recorded in another file, such as a C# registration in `Program.cs`, `line` is the declaration and `site` names the place the lean row shows. `analyze_impact` and `find_tests` also give `completion.total`, the number of rows the search found before `max_rows`, `max_bytes` or a page cut the list. When `total` is more than the rows shown, the difference is what was left out. A search stopped by `max_depth` or its node budget found only part of what may be affected, so `total` counts that part, and the answer's limitations say so. A `find_tests` row already carried `id`, `line` and `evidence`. No other tool sets `completion.total`.

## Cross-repository symbols (FR900 to FR904)

A library and the applications that use it are often separate repositories. When they are registered in one workspace (`proofmesh workspace add <name> <repository>...`) and the workspace is linked (`proofmesh workspace link <name>`), the link file holds a `package_symbol` link (link format 0.3) for each TypeScript `calls`, `inherits`, `implements` or `references` site in one member that resolved to a symbol of an installed npm package another member builds. The package is matched by the name in the building member's `package.json`; the symbol by its name inside its file (`Point.norm` for `src/point:Point.norm`), which is how the installed declaration file names it. The same version installed (the TypeScript adapter's external input `npm:<name>/<version>`) as built (the `version` of that `package.json`) is `observed`; another or an unknown version is `inferred`. Two members building one package, or two symbols of one name in it, make a candidate naming every target, and no row is resolved. A package no member builds makes no link: its sites stay `resolved_external`, as without a workspace.

`get_relationships`, `analyze_impact`, `find_tests` and `trace_paths` take `include_workspace: true`, answered from the latest link file of each workspace that holds the repository; nothing is matched at query time.

- `get_relationships` lists the inbound sites in other members after the subject's own rows, each with `repository` (id, name and commit). Its ids and evidence ids are of that repository's snapshot, so `read_evidence` reads them with that `repository_id`. A lean row ends `repo=<name>@<commit>`.
- `analyze_impact` adds each such site as a dependent one deeper than what it reaches, and that site's own dependents in its repository after it. Each carries `line`, `relationship` and `site` as a local row does (FR860), read from its own repository's snapshot, and `completion.total` counts it. `by_project`, `by_area` and `by_team` still count this repository's dependents only.
- `data.workspace` names each workspace, its link file and each member's side of it: the snapshot and commit the link file was built from, and `current`. A side re-indexed since is named in a limitation, with the `workspace link` command that seals a current file. This repository's symbols are matched to an older link file by stable key.
- A version mismatch is the limitation `version mismatch: app uses 1.1.0, lib is 1.2.0`, and its rows are `inferred`.
- `find_tests` (FR1260) adds the tests of other members that reach the subjects through those links, from the sites linked to the subjects or to what reaches them here. Each carries `repository` and a depth one more than its linked site's; its `chain` runs in its own repository and its last hop is the call that crosses out of it. `totals` counts them; `by_project` does not.
- `trace_paths` (FR1261) takes a symbol of another member as `source_id` or `target_id`, by its id in that member's side of the link file, and a path crosses from a call site into the member its `package_symbol` link names. Such nodes carry `repository`; the crossing hop's relationship has the rule `package_symbol` and the link's basis. Dispatch is not followed across repositories.
- A chain crosses any number of members (FR1262): from what `analyze_impact` or `find_tests` reached in one member, the members that use a package it builds follow, one deeper each, but never back into the repository asked. A path through a library, an application that publishes a package and an application of that is one `trace_paths` answer.
- Not yet: other ecosystems than npm.

## Structural search: `search_structure` (FR1060 to FR1067)

`search_structure` (profile `extra`) finds code by its shape, where `search_sources` finds text. A pattern is code in its language with ast-grep's metavariables, matched over the Tree-sitter grammars the syntax tier ships, with ast-grep's default (smart) matching: comments and punctuation the pattern leaves out are skipped. It reads the content the snapshot captured, never the working tree, and a limitation names that snapshot and its commit.

```
search_structure { "pattern": "$D.escape($A)", "language": "typescript", "scope": { "reachable_from": ["DataSource.initialize"] } }
search_structure { "pattern": "try { $$$ } catch ($E) {}", "language": "typescript", "path_prefix": "src/" }
search_structure { "pattern": "for (const $X of $Y) {\n  $$$\n  await $Z\n  $$$\n}", "language": "typescript" }
```

- **Metavariables.** `$X` matches one named node, `$$X` one node named or not, `$_` one node without capturing, `$$$X` and `$$$` any number of nodes (taken until the next pattern node matches, never backtracking). A metavariable used twice matches only equal code. In Python, Go, Rust, C# and the other languages where `$` is not an identifier character, the pattern is rewritten as ast-grep rewrites it, so the same pattern text works.
- **Languages.** `typescript` (`.ts`, `.cts`, `.mts`), `tsx`, `javascript` (read with the TSX grammar), `python`, `go`, `rust`, `java`, `c`, `cpp`, `csharp`, `ruby`, `kotlin`, `scala`, `swift`, `bash` and `hcl`, each over the extensions ast-grep gives it. With no `language`, each file is searched in the language of its extension, a language the pattern does not parse in is skipped and named, and files with no grammar are counted by extension.
- **Scope.** `reachable_from` and `reaching` take symbols (an id, `{ name, path }`, or a name the snapshot holds once, such as `DataSource.initialize`). A match is kept when its enclosing symbol, the innermost symbol that holds it whole, is one `trace_paths` reaches from them (or that reaches them), within `max_depth`. Reaching a class does not put its methods in scope. `importing` takes file paths and keeps the matches in the files that import one. Keys intersect.
- **Rows.** Lean: `<enclosing name> <path>:<line> <first line of the match>`, the text cut at 120 characters and quoted as JSON when it holds a space. JSON (`compact`, `full`): `data.matches[]` with `path`, `line`, `end_line`, `text` and `symbol` (`id`, `key`, `kind`, `name`, `qualified_name`), and `data.totals`. A match inside another match is listed too, as ast-grep lists it.
- **Refusals.** A pattern that does not parse in its language, one that is more than one node, and a lone `$$$` are `INVALID_ARGUMENT` before any file is searched. The message names each syntax error with its line and column, and `details.syntax_tree` is the pattern as ast-grep's `--debug-query=pattern` prints it:

  ```
  the pattern does not parse as typescript: syntax error at 1:1 in "foo($A"
  ERROR
    identifier foo
    (
    MetaVar $A
  ```

- **Bounds.** A pattern is untrusted input that runs over captured source, so it is bounded and never run. The match runs in the syntax adapter's own process with a minimal environment and a 1 GiB heap. That process stops at `timeout_ms` and returns what it found, and it is killed one second later if it has not stopped. A pattern is at most 4,096 characters. A file over 1 MiB is not parsed, and one search reads at most 64 MiB of source; both are counted in a limitation. The matcher keeps only the rows of the page asked for, so `max_rows` pages with a cursor and `completion.total` counts every match. After a timeout, the total counts the matches found before it.
- `bench/structure` compares every answer with the pinned ast-grep CLI. Every match set is the same. On the parity fixture, each TypeScript pattern takes at most 2 s of CPU time at p95 (FR1880). That covers a whole MCP session: the server's startup and the matcher. 1.4 s was the most measured. ast-grep's native, multi-threaded CLI is still faster, at 240 to 300 ms of CPU and 35 to 100 ms of wall-clock time per pattern, against 0.3 to 1.4 s of wall-clock time for `search_structure`. The benchmark prints both tools' times beside each pattern.

## Graph query: `query_graph` (FR960 to FR966)

`query_graph` (profile `extra`) answers a question that no typed tool answers in one call with one bounded, read-only query in a subset of openCypher. Typed tools come first: they follow dispatch through interfaces, list candidate and unresolved sites, and page. `query_graph` reads only what the snapshot resolved. Examples:

```
MATCH (:function {name: 'main'})-[:calls*1..6]->(c)-[r:calls]->(:function {name: $target}) WHERE NOT c.test RETURN r
MATCH (u:file)-[:imports]->(:file {path: 'src/api/handler.ts'}) WHERE u.path STARTS WITH 'src/api' RETURN DISTINCT u
MATCH (f:function) WHERE f.path STARTS WITH 'src/' AND NOT EXISTS { (x)-->(f) WHERE x <> f } RETURN f
```

The grammar. Keywords are case-insensitive. A name in backticks is a name, never a keyword. `//` starts a comment.

```
query       = match { match | with } return [";"]
match       = ["OPTIONAL"] "MATCH" pattern { "," pattern } ["WHERE" expr]
with        = "WITH" projection ["WHERE" expr]          (an expression item needs AS)
return      = "RETURN" projection
projection  = ["DISTINCT"] ("*" | item { "," item }) ["ORDER BY" expr ["ASC"|"DESC"] {"," ...}] ["SKIP" n] ["LIMIT" n]
item        = expr ["AS" name]                           (count and collect only as a whole item)
pattern     = [name "="] node { rel node }
node        = "(" [name] [":" label { "|" label }] [props] ")"
rel         = ("-" | "<-") ["[" [name] [":" type { "|" type }] ["*" [min] ".." max | "*" n] [props] "]"] ("-" | "->")
props       = "{" key ":" expr { "," key ":" expr } "}"
expr        = OR, XOR, AND, NOT; = <> != < <= > >=; STARTS WITH, ENDS WITH, CONTAINS, IN, IS [NOT] NULL; + -;
              literals (strings, numbers, true, false, null, [lists]), $params, name, name.key,
              pattern predicates such as (a)-[:calls]->(), EXISTS { [MATCH] pattern [WHERE expr] },
              count(*), count([DISTINCT] e), collect([DISTINCT] e), type(r), labels(n), size(e), toLower(e), toUpper(e)
n, min, max = whole numbers, or a $param for SKIP and LIMIT
```

- **Nodes.** A label is a symbol kind of the snapshot format (`function`, `class`, `method`, `interface`, `module`, `endpoint`, `table`, ...), `file` or `external`. A file and its module symbol are one node, labelled both `file` and `module`, so imports, which run between files, and calls from top-level code meet at the same node. A symbol has `id`, `kind`, `name`, `qualified_name` (`src/store:Store.save`), `path`, `line`, `end_line`, `signature`, `key` (its stable key) and `test`. A file has `id`, `kind` (`file`), `name`, `path`, `line` (1), `language`, `disposition` and `test`. An external symbol has `id`, `name` and `module`. An unknown label is refused with the list of valid ones.
- **Relationships.** A type is an assertion type of the snapshot format (`calls`, `imports`, `implements`, `references`, `inherits`, ...). A relationship is an assertion the snapshot resolved, in the repository or to an external symbol. Candidate, ambiguous and unresolved sites are not relationships here, and there is no dispatch from an interface or base member to its implementations: write it as a pattern, such as `(c)-[:calls]->(m)<-[:implements]-(impl)`. A relationship has `id`, `type`, `resolution`, `origin`, `basis`, `path` and `line`, its site.
- **Variable-length paths** need an upper bound of at most 6, or `max_depth` when that is lower (`*1..3`, `*..4`, `*2`). `*` alone, `*1..` and a bound above 6 are refused before the query runs, and the refusal names the bound. A variable-length pattern reaches each node once, at its shortest distance, so it returns one row per node, not one per path. A node whose shortest distance is below the lower bound is not returned.
- **Read only.** `CREATE`, `MERGE`, `SET`, `DELETE`, `DETACH`, `REMOVE`, `CALL`, `LOAD`, `FOREACH` and `DROP` are refused by name wherever they appear outside a string, before anything runs. So are `=~` (no regular expressions), any function not listed above, and `UNWIND`, `UNION`, `CASE` and `shortestPath`. A query is parsed into a plan and run by an interpreter over fixed prepared statements on the snapshot, which is opened read only. No SQL is built from the query. `$name` parameters are values in `params`, compared as values and never spliced into the text. A parameter the query uses but `params` lacks is refused.
- **Bounds.** `timeout_ms`, `max_rows` and `max_bytes` bound a query as they bound other tools (defaults 10 s, 100 rows, 64 KiB; at most 30 s, 1,000 rows, 1 MiB). A query that would pass the time or row limit stops there. It returns the rows found so far, `completion.stop_reasons` names the limit, and a limitation says it in lean, for example `# Stopped at max_rows 100; the rows are those found before it.` Rows held for `count`, `collect`, `ORDER BY` or `DISTINCT` count against `max_rows` before aggregation, and a count cut that way says so. `query_graph` does not page.
- **Rows.** Lean is the default over MCP. The header names the snapshot's commit: `# query_graph · commit <sha> · <n> rows · <snapshot> current`. Each result row is one line, built from its first node, relationship or path:
  - a node is `<name> <path>:<line> <kind>`, and a file is `<path>:1 file`;
  - a relationship is the source's name at the site's `path:line`, then its type, as `get_relationships` lists an inbound row;
  - a path is one line per node, at its declaration, with `depth=<n>` from the second node on.

  The other columns follow as `<column>=<value>` tags. A row ends with `inferred` when any relationship it was matched through is inferred (FR181). A row of scalars alone is its tags. `envelope: "compact"` or `"full"` gives `data.columns` and `data.rows` (each `{ values, inferred? }`, a node as `{ id, kind, name, path, line, key }`, a relationship as `{ id, type, from, to, from_name, to_name, path, line, basis }`), and `evidence_ids` covers every returned node's declaration and relationship's site.
- `bench/parity` asks its twelve questions through `query_graph` too, one query each (`queryGraphQuery` in `bench/graph-bench/lib.mjs`). It scores each answer beside the typed tools' answer, says whether their items are the same, and reports the p95 time.

## Analyser findings: `get_findings` (FR1900 to FR1905)

Proofmesh does no data-flow or taint analysis of its own (#30). It imports the findings that CodeQL, Opengrep or another analyser wrote as SARIF 2.1.0 and shows them on the symbols an agent changes. It runs no analyser and needs no analyser licence; which analysers produce the file is the person's choice.

- `proofmesh sarif add <repository> <file.sarif> [--name N]` reads every run of the file against the repository's current snapshot. Results are deduplicated by tool, rule and location. A result outside the repository, in a file the snapshot does not index, or with no location is not attached: the command prints each with its reason (`outside_repository`, `not_in_snapshot`, `no_location`), and `get_findings` counts them in its limitations. Each file a finding is in has its hash recorded as the tree stands, as for a SCIP index. Importing a file of the same name again replaces it. `sarif list` and `sarif remove` manage imports.
- `get_findings` (profile `extra`, JSON) takes `subject_ids`, `paths`, or neither for every finding. Each finding has `tool` (with its version), `rule`, `level`, `message`, `path`, `line`, `end_line`, `rank` and `precision` when the tool gave them, and `symbol`: the innermost symbol at the line, as `get_symbols_at` picks it, or the file's module.
- A finding whose file's content in the asked snapshot differs from the file at import is `stale: "sarif_stale:<name>"`, because its line may have moved. It stays stale until a new SARIF file is imported.
- `analyze_impact` dependents and `find_tests` rows carry `findings`, the number of findings on that symbol, when there are any. In lean the tag is `findings=<n>`. A row from another repository of the workspace carries none.

## Change coupling: `get_cochanges` (FR2020 to FR2025)

Some files must change together though no import, call or reference links them: a migration and its model, a serializer and its client, a doc and the code it describes. `analyze_impact` and `impact_completeness` follow relationships only, so they cannot name these. `get_cochanges` reads them from the repository's own git history.

- History is read with `git log` on the registered root, from the snapshot's commit backwards, with discovery's environment allowlist and a timeout; nothing is fetched (FR2024). `window` is `{ days: n }`, counted back from that commit's date (default 365), or `{ commits: n }`; at most 10,000 commits are read either way. The window ends at the snapshot's commit, never at the clock, so one snapshot always gives one answer. Renames are followed; merge commits are left out, so each change counts once, on its own commit. The reader (`packages/proofmesh/src/indexer/history.ts`) and its per-snapshot cache are shared with the history tools to come (#238, #240).
- `get_cochanges` (profile `extra`, lean by default) takes `paths` (any file of the snapshot, analysed or not) or `subject_ids` (a symbol stands for its file). Per subject, its partners are ordered by `degree`, then `shared`, then path; `degree = shared / min(subject_commits, partner_commits)` over the window (FR2021). A pair is listed when it shares at least `min_shared` commits (default 3) with a degree of at least `min_degree` (default 0.3). A commit touching more than `max_files_per_commit` files (default 50) forms no pairs and is counted in the limitations. A partner the snapshot does not hold is left out.
- Each row carries `linked`, whether any resolved or candidate relationship of the snapshot joins the two files in either direction at depth 1, with its `relationship_types`, and `test` for a partner in test code; `only_unlinked: true` leaves linked partners out. A row never carries a `basis`: co-change is not a relationship and no traversal tool follows it (FR2022). A lean row is `<path> shared=<n> degree=<d> [linked] [test]`, with `of=<subject>` when there are several subjects (FR2025).
- With no usable history the answer has no rows and says why: `no_history` (the root is not a git working tree, or lacks the snapshot's commit) or `history_shallow` (a shallow clone, read as far as it goes). The limitations always state the thresholds and the number of commits read; squash merges make coupling coarser.
- `impact_completeness` with `include_cochanges: true` adds `cochange`: each partner of a file the diff touches that the diff does not change, as `{ ...row, of, status: "not_changed" }`, from the history up to `base`, so the change under review does not vote on what usually changes with it. Its lean rows are `cochange <path> shared=<n> degree=<d> [linked] not_changed (with <file>)`. Without the flag the answer is as before (FR2023).
